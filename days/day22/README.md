# 第 22 天：链式、路由与并行

> 最后核对：2026-11-04

第 21 天写了一条固定流程：想搜索词 → 搜索 → 读网页 → 作答。今天在它上面学三种最常用的工作流模式：

- **链式**：一步的输出是下一步的输入，步骤之间加检查（第 21 天已经做了一个）
- **路由**：先给问题分类，再交给不同的 prompt、工具和模型。「你好」不用走研究流程，更不用强模型
- **并行**：互不依赖的事同时做。几个搜索词同时搜，几次分类同时发，再投票

```text
$ node days/day22/exercise/router.ts "我们的网关怎么回滚？"
（走 docs，用 openai:my-cheap-model）

执行 tide rollback --to previous，大约 2 分钟完成 [1]。回滚以后在 #incident 频道里同步进展 [1]。

来源：
[1] 本地文档 ops/oncall.md
```

学完今天，你会：

- 用便宜的模型做分类，把问题路由到不同的处理方式，并在评估集上测出准确率
- 写一个有并发上限的并行执行器，结果顺序稳定、一项失败不影响其他项
- 用多次分类加投票，换取更稳定的结果
- 知道什么时候并行能省时间，什么时候反而会更慢

## 链式：每一步之间加检查

链式（prompt chaining）是把一个任务拆成几步，每一步调用一次模型，上一步的输出交给下一步。第 21 天的固定流程就是一条链。拆开的好处是每一步都更简单、更好调；坏处是**错误会往下传**：第一步的搜索词不合格，后面搜到的、读到的、答出来的全都跟着错。

所以链的每一环之间要有一道检查（gate）。第 21 天的 `parseQueries()` 就是：格式不对、是空的，就退回到保守的做法。检查不一定是代码，也可以是一次便宜的模型调用，比如「这份资料和问题相关吗？只回答是或否」。原则是**检查要比被检查的那一步便宜**，否则不如把那一步做好。

## 路由：先分类，再分流

研究助手现在对每个问题一视同仁：同样的 system prompt、同样的十几个工具、同样的强模型。可是用户的问题差别很大：

| 类别 | 例子 | 怎么处理 |
|---|---|---|
| chat | 你好；把这句话翻译成英文；什么是灰度发布 | 便宜的模型直接回答，不带工具 |
| docs | 我们的网关怎么回滚；错误码 TIDE_E2077 是什么 | 便宜的模型，只带本地文档的三个工具，专门的 prompt |
| research | 潮汐协议 3.0 快了多少；对比三家搜索 API 的价格 | 强的模型，完整的研究助手 |

[router.ts](exercise/router.ts) 的 `routeQuestion()` 先调用 `classify()` 分类，再走对应的路。分类本身也是一次模型调用，所以它必须**又便宜又快**：

- 用便宜的模型。在 `.env` 里填 `CHEAP_MODEL`（和 `OPENAI_*` 同一个服务，只换模型名），不填就用默认的模型
- 只输出一个很短的 JSON，用 `maxTokens` 限制长度
- prompt 里写清楚每个类别的边界，再加一句「拿不准时选 research」

### 分错了怎么办

分类器一定会分错。关键是**分错的代价不对称**：

- 把研究问题分成 chat：便宜的模型凭记忆回答一个它不知道的数字，很可能编一个出来。这是最糟的
- 把 chat 分成 research：多花了一些钱和时间，但答案没问题

所以解析不了、拿不准的时候，都走 `FALLBACK_ROUTE`，也就是最稳妥的 research。另一个兜底：分到 docs，但没有配置本地文档，也改走 research。

### 测出准确率

路由器的好坏要用数据说话。[data/routes.ts](data/routes.ts) 有 24 个标好类别的问题，其中几个故意放在边界上：同样提到「潮汐」，问「我们的网关怎么部署」是 docs，问「潮汐协议 3.0 的发布说明怎么说」是 research。

`evaluateRouter()` 跑一遍，给出准确率、分错的问题，还有**混淆矩阵**：

```text
| 应该 \ 实际 | chat | docs | research |
|---|---|---|---|
| chat | 7 | 0 | 1 |
| docs | 0 | 6 | 2 |
| research | 0 | 0 | 8 |
```

（示意的数字。）准确率只告诉你错了几个，混淆矩阵告诉你**错在哪里**：上面这张表里，错误都在对角线的右边，说明它宁可多查也不乱答，这正是我们想要的方向。如果 research 那一行有数字落在 chat 列，就要认真改 prompt 了。

## 并行：同时做，但有上限

固定流程里的几个搜索词互不依赖，没必要等第一个搜完再搜第二个。串行时总耗时是每一步**加起来**，并行时是**最慢的那一步**。

但不能一下子全发出去。模型服务和搜索服务都限制了并发数和每分钟的请求数，同时发几十个请求，会收到一堆 429，重试（第 9 天）反而更慢。所以要有一个**并发上限**。

[parallel.ts](exercise/parallel.ts) 的 `mapLimit(items, limit, fn)` 做三件事：

1. 同时最多 `limit` 个在跑，做完一个就开始下一个
2. 结果的顺序和输入一致，不管谁先做完
3. 一项失败不影响其他项，每一项的结果是 `fulfilled` 或 `rejected`，和 `Promise.allSettled` 一样

第 2 点很容易被忽略，却很重要。`gatherMaterials()` 改成并行以后，如果按「谁先搜完」的顺序合并，同一个问题每次跑出来的资料顺序、来源编号都可能不同：测试不稳定，用户看到的引用编号也会变。按输入的顺序合并，并行的结果就和串行时**一模一样**，只是更快。

实现的思路是开 `limit` 个「工人」，每个工人做完手上的就去领下一项：

```ts
async function worker() {
  while (next < items.length) {
    const index = next++;   // 单线程：这一行不会被别的工人打断
    // 执行 fn(items[index])，结果放进 results[index]
  }
}
await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
```

### 投票：用并行换稳定

并行还有另一种用法：**同一件事做几次，取多数**。模型的输出有随机性，边界上的问题这次分成 docs、下次分成 research。`classify(question, model, { votes: 3 })` 同时发出三个一样的请求，用 `vote()` 取出现最多的，`agreement` 是得票的比例。三票全一样，说明这个问题很明确；两票对一票，说明它在边界上，值得记下来，加进评估集。

投票不是免费的：三次分类，三倍的钱。分类用的是便宜的模型、输出又很短，三倍也不多；但对研究这种贵的步骤投票，就要掂量一下了。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 并行越多越快 | 超过服务的并发限制会被限流，重试反而更慢。要有上限 |
| `Promise.all` 就是并行执行器 | 它没有上限，而且一个失败就整体失败，拿不到其他项的结果 |
| 并行以后结果的顺序无所谓 | 顺序不稳定，来源编号就会变，测试也会时好时坏。按输入的顺序合并 |
| 路由要用最强的模型才分得准 | 分类是简单任务，便宜的模型通常就够。用评估集测出来再决定 |
| 准确率高就够了 | 要看错在哪里：把研究问题分成闲聊，比反过来糟糕得多 |
| 投票总能提高效果 | 它换来的是稳定，代价是几倍的成本。用在便宜又关键的步骤上 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说期望 `['第 0 个', '第 1 个', …]`，顺序乱了 | 结果用 `push` 按完成的顺序放，没有按 `index` 放 |
| 测试说「同时跑的不能超过 2 个」，实际是 1 | 还是串行，比如在循环里 `await` 了每一项 |
| 测试说「平票取先出现的」 | 比较时用了 `>=`，平票时被后面的替换了 |
| 测试说「三个请求要同时发，不是一个接一个」 | 分类几次用的是 `for` 循环里的 `await` |
| 测试说「分类和回答的用量都要算上」 | 只返回了回答的用量 |
| 没有配置本地文档时报错说读不到 `root` | 分到 docs 时没有检查 `setup.docs`，要改走 research |
| 测试说「出错的不算进混淆矩阵」 | 把 `error` 当成一个类别去计数了 |

## 小结

- 链式：一步接一步，每一步之间加一道比它便宜的检查
- 路由：便宜的模型分类，不同的问题交给不同的 prompt、工具和模型。分错的代价不对称，拿不准就走最稳妥的路
- 用评估集测路由器，看准确率，更要看混淆矩阵
- 并行要有上限，结果按输入的顺序合并，一项失败不影响其他项
- 投票用几倍的成本换稳定，适合便宜又关键的步骤
