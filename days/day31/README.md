# 第 31 天：评估入门

> 最后核对：2026-11-07

第三阶段结束时，研究助手 v2 已经能拆问题、派子 Agent、核查引用。可它到底有多好？到现在为止，我们的判断方法一直是「跑几个问题看看」。这个办法撑不过第一次改 prompt：你把 system prompt 里的一句话改得更清楚，试了三个问题都变好了，上线以后发现另外十几类问题变差了。

今天开始第四阶段：**工程化**。第一件事是评估。今天先搭一个最朴素、但能用的评估：一份 25 条的评估集，一个能并行跑完它们的运行器，一套用代码检查期望的规则，最后输出一张按类别统计的表。

```text
$ node days/day31/solution/eval/cli.ts
用 openai:my-model 跑 25 条用例……
[1/25] · web-release-date（8.2 秒）
……
| 分组 | 条数 | 通过 | 通过率 | 出错 |
|---|---|---|---|---|
| all | 25 | 19 | 76% | 0 |
| web | 13 | 11 | 85% | 0 |
| docs | 11 | 9 | 82% | 0 |
| multi-hop | 2 | 1 | 50% | 0 |
| unanswerable | 3 | 1 | 33% | 0 |
……
没通过的：
- unanswerable-v4：资料里没有答案，但回答没有说没查到
- multi-config-upgrade：缺少 handshake.attempts
```

学完今天，你会：

- 说清楚单元测试、离线评估、线上监控各自负责什么
- 从真实的使用场景出发写评估用例，知道一条好用例长什么样
- 把评估集存成 JSONL，解析、校验、按标签挑选
- 写一个并行、出错不中断的评估运行器，按类别统计通过率

## 为什么 Agent 必须有评估

普通的函数，输入一样输出就一样，写几个单元测试就能放心。Agent 不是这样：

- **输出不确定**：同一个问题跑两次，搜索的关键词、读的网页、回答的措辞都可能不同
- **改动的影响是全局的**：改一句 system prompt、换一个模型、加一个工具，影响的是所有问题，不是你正在看的那一个
- **失败是概率性的**：一个问题 10 次里错 2 次，你试一次很可能看不出来

所以「它好不好」不是一个能靠看几眼回答的问题，而是一个**统计**问题：在一组有代表性的问题上，答对的比例是多少？改动以后，这个比例变了多少？哪一类问题变了？

## 三种检查，各管一段

| | 单元测试（第 7 天起） | 离线评估（今天起） | 线上监控（第 34 天起） |
|---|---|---|---|
| 测什么 | 代码的逻辑：循环、护栏、解析 | Agent 整体的表现：答得对不对、引用准不准 | 真实用户遇到的情况 |
| 用什么模型 | mock 模型，脚本写死 | 真实模型 | 真实模型 |
| 结果 | 通过或失败，必须 100% 通过 | 一个比例，比如 76% | 一条条 trace、报错和用户反馈 |
| 什么时候跑 | 每次提交 | 改 prompt、换模型、加工具之前和之后 | 一直在跑 |
| 花钱吗 | 不花 | 每跑一遍都花 | 已经花了 |

它们互相补不上。单元测试再全，也测不出「模型看到这个工具描述会不会用错」；离线评估再多，也覆盖不了用户真实会问的千奇百怪的问题；线上监控能发现问题，但发现时用户已经遇到了。线上发现的问题，要变成评估集里的新用例：这是评估集成长最主要的来源。

## 一条用例长什么样

打开 [research.jsonl](data/eval/research.jsonl)：

```json
{"id": "web-latency", "question": "潮汐协议 3.0 和 2.x 建立连接的平均延迟分别是多少？",
 "tags": ["web", "fact"], "expected": {"facts": ["18", "42"], "sources": ["/benchmark.html"]}}
```

（实际文件里一条占一行，这里为了好读折了一下。）

- **id**：唯一，定下来就不改。第 33 天对比两次评估的结果，就靠它对上号
- **question**：用户会怎么问。尽量照搬真实用户的原话，包括不完整、有错别字、指代不清的
- **tags**：分组统计用。整体通过率从 80% 掉到 76%，你要知道是哪一类掉的
- **expected**：能用代码检查的期望

`expected` 里能写的：

| 字段 | 意思 | 例子 |
|---|---|---|
| `facts` | 回答里一定要有的事实，每一项可以是几种等价的写法 | `[["2026 年 3 月 14 日", "3 月 14 日"]]` |
| `forbidden` | 回答里不能有的：常见的错误答案 | 企业版的价格不能写成托管的 499 |
| `sources` | 应该引用的来源 | `"/pricing.html"`、`"doc:guide/config.md"` |
| `unanswerable` | 资料里没有答案，应该说没查到 | 「潮汐协议 4.0 什么时候发布？」 |
| `tools`、`maxToolCalls` | 应该调用的工具、最多调用几次 | 闲聊的问题 `maxToolCalls: 0`。第 32 天用 |

### 为什么用 JSONL

一行一条用例。追加一条就是加一行；在代码评审里，改了哪几条一目了然；文件很大时可以一行一行地读。我们还允许 `//` 开头的注释行，用来给用例分节、写说明。评估集是要长期维护的代码，和代码一样要评审、要版本管理（第 33 天）。

## 评估集从哪里来

第一版评估集最常见的错误，是坐下来凭空想 50 个问题。凭空想的问题往往太规整、太像你自己会问的，覆盖不到真实用户的问法。更好的来源，按可靠程度排：

1. **真实用户的问题**：日志、客服记录、用户反馈。研究助手还没上线，可以先用你自己和同事这一个月真实问过的
2. **线上的失败**：每一个用户报告的错误，修好之前先写成用例。这样同一个错误不会再犯第二次
3. **按能力补齐**：真实问题凑不齐的类别，再有意识地补。今天的评估集分了几类：

| 类别 | 考的是 | 条数 |
|---|---|---|
| web | 搜索、读网页，找到单个事实 | 9 |
| docs | 查本地文档，包括换了说法的问题 | 8 |
| multi-hop | 把网页和本地文档连起来 | 2 |
| compare、calc | 对比、计算 | 2 |
| unanswerable | 资料里没有答案，要说没查到 | 3 |
| chat | 闲聊，不该去查资料 | 1 |

**unanswerable 这一类特别重要**。一个总能「答出来」的研究助手，比一个偶尔说「没查到」的危险得多。没有这类用例，你永远测不出它会不会编。

### 先做 20–50 条

不要一开始就追求几百条。20 条认真写的用例，比 500 条自动生成的更有用：

- 每一条你都看过回答，知道它为什么对、为什么错
- 跑一遍几分钟、几毛钱，改一次 prompt 就能跑一次
- 足够发现「整体变差了 20%」这种大问题

它的局限也要心里有数：25 条用例，一条的变化就是 4 个百分点。今天的 76% 和明天的 72%，很可能只是随机波动（第 32 天会讲怎么看方差）。用例多了，这个数字才稳。

### 环境要固定

评估集里所有的答案，都只在**假互联网**（[data/web.ts](data/web.ts)）和**本地文档**（`data/docs/`）里。第 12–30 天它一直放在 `tests/` 下，今天挪到 `data/`，评估也用它。

为什么不直接用真实的搜索？因为真实的网页每天在变。今天 76%、明天 72%，你分不清是 Agent 变差了，还是搜索结果变了。回归评估要的是「只有被测的东西在变」。真实环境的表现，交给线上监控。

| 其余文件 | 和第 30 天的参考答案一样 | 不用改 |

几个设计上的选择：

- **target 是一个函数**：`(用例) => Promise<TargetOutput>`。研究助手、固定流程、深度研究，包一层就能用同一套评估集。第 33 天横评不同的模型、第 36 天比较省钱前后的版本，都靠它
- **每条用例一套新的配置**：新的工作目录、新的来源登记。用例之间互不影响，换个顺序跑，结果也一样
- **出错不中断**：某条用例超时了，记下来，接着跑别的。一个改动让三条用例开始报错，正是评估要发现的
- **检查和运行分开**：`runEval` 只负责跑、记下原始的输出；`checkExpectations` 再去判断对错。原始输出存下来以后，改了检查规则可以重新算分，不用再花钱跑一遍。第 32 天的评分器就是这样接上的

## 常见误解

| 误解 | 实际上 |
|---|---|
| 有单元测试就够了 | 单元测试用 mock 模型，测的是代码的逻辑，测不出模型的行为 |
| 评估集越大越好，先生成几百条 | 先做 20–50 条你看得懂的。条数多但质量差，分数没有意义 |
| 让模型生成用例最省事 | 可以用来补充，但要人看过。模型生成的问题太规整，期望也可能是错的 |
| 通过率 100% 才算好 | 评估集应该有难题。全部通过，说明它测不出下一次改动的好坏了 |
| 评估要用真实的搜索才真实 | 回归评估要固定环境，否则分不清是谁在变。真实环境交给线上监控 |
| 用例写好就不用动了 | 线上的每个失败都要变成新用例，过时的用例要改或者删 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说「两行有问题，两条都要报，不能遇到第一个就停」 | 解析遇到第一个错误就抛出了，没有收集完所有的问题 |
| 测试说 `parseDataset` 的结果里缺了 `forbidden: []` 之类的字段 | 放进结果的是 `JSON.parse` 的原始数据，不是 `safeParse` 返回的 `data`（补上了默认值） |
| 测试说 `maxToolCalls: 0 也是一种期望` | 用 `!expected.maxToolCalls` 判断，把 0 当成了没写 |
| 测试说结果「按用例的顺序，不按完成的先后」 | 跑完一条就 `push` 一条，顺序变成了完成的先后 |
| 测试里 `runEval` 直接抛出了「模型超时」 | 没有用 try/catch 把 target 的错误记成这条用例的 `error` |
| 测试说同时最多 concurrency 条，实际是 1 或者 4 | 还在用 for 循环一条条跑，或者直接 `Promise.all` 了全部 |
| `summarizeRun` 的 byTag 顺序不对 | 按标签排序了。要按标签第一次出现的顺序 |

## 动手：搭起第一版评估

按顺序做，每做完一步就运行一次 `npm run check 31`：

1. **TODO 1**：解析 JSONL，收集所有的问题、带上行号。
2. **TODO 2**：校验整个评估集：重复的 id、没有期望的用例、自相矛盾的用例。
3. **TODO 3**：用代码检查一条用例的期望。
4. **TODO 4**：运行器：在并发上限内同时跑，出错记下来，结果按用例的顺序。
5. **TODO 5**：汇总：整体和每个标签的通过率，没通过的原因。全部测试通过。
6. **加几条你自己的用例**：至少 5 条，写在 `research.jsonl` 里。想想研究助手最可能在哪里出错：两个来源说法不一致的、问题里有错别字的、要先算一下的。写完运行 `node days/day31/exercise/eval/dataset.ts days/day31/data/eval/research.jsonl` 检查格式。

## 检查

```bash
npm run check 31
```

用真实模型跑一部分评估集（每类挑两条），打印汇总：

```bash
npm run check 31 -- --e2e
```

跑完整的评估集（需真实模型，配好 `.env` 里的模型和 embedding）：

```bash
node days/day31/exercise/eval/cli.ts
```

只跑某一类，或者某几条：

```bash
node days/day31/exercise/eval/cli.ts --tags unanswerable
```

结果存在 `evals/` 下面。打开 JSON 看看没通过的用例：模型到底回答了什么？调用了哪些工具？很多时候你会发现，问题不在模型，而在用例本身：期望写得太死、问题有歧义。这时候改的是用例。

## 小实验

- 同一个评估集连续跑三遍，看看每一遍的通过率差多少、哪几条时对时错。这就是第 32 天要讲的方差
- 把 `RESEARCH_PROMPT` 里「不知道就说不知道」之类的话删掉，只跑 `--tags unanswerable`，看看通过率怎么变
- 把 `concurrency` 从 2 改成 8，看看总耗时和耗时的中位数各变了多少，有没有触发限流
- 统计一下没通过的用例里，有几条是用例本身写得不对（期望太死、问题有歧义），改掉它们
- 把同一个问题换三种问法（口语化、带错别字、只说一半），各写一条，看看研究助手在哪种问法上最容易出错

## 小结

- Agent 的输出不确定、改动的影响是全局的，「它好不好」是一个统计问题，要靠评估回答
- 单元测试管代码逻辑，离线评估管整体表现，线上监控管真实用户。三者互相补不上
- 一条用例：唯一的 id、用户的原话、分组的标签、能用代码检查的期望。没有期望的用例没有意义
- 评估集从真实的问题和线上的失败里来，按能力补齐。一定要有「资料里没有答案」的用例
- 先做 20–50 条你看得懂的；环境要固定，分数才能前后比较
- 运行和检查分开：原始输出存下来，改了检查规则可以重新算分

## 想一想

- 今天的检查只看「事实出没出现」。一个回答事实全对，但啰嗦、结构混乱，它算好吗？一个回答写了「18 毫秒」，但说成是 2.x 的延迟，代码检查能发现吗？（第 32 天）
- 25 条用例，通过率从 76% 变成 72%，这说明改动让它变差了吗？要跑几遍、要多少条用例，你才敢下结论？（第 32、33 天）
- 每次改 prompt 都要记得手动跑一遍评估，你多半会忘。怎么让它自动跑，并且告诉你哪几条变了？（第 33 天）
