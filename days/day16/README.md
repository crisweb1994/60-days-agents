# 第 16 天：上下文工程（下）：长任务不失忆

> 最后核对：2026-11-02

昨天的研究助手在上下文快满时，会把最旧的对话整轮删掉。这很安全，但很粗暴：用户在第一轮说的「报告要写给不懂技术的老板看」，二十轮之后就消失了，模型开始写满是术语的报告。

今天换一种做法：上下文快满时，**按代价从小到大**依次尝试三种办法，尽量保住有用的信息：

1. **清理旧的工具输出**：十轮之前读过的网页，留一行说明就够了，要用可以重新读
2. **大结果写入文件**：太长的工具结果，一开始就不全放进上下文，只放开头和文件的位置
3. **摘要压缩**：让模型把较早的几轮对话写成一份结构化的摘要，替换掉原来的对话

最后，压缩一定会丢东西。今天还要写一个测试：压缩以前埋下几个关键事实，压缩以后检查它们还在不在。

```text
你 > 帮我整理一下前面查到的所有资料
（把较早的 6 轮对话压缩成了摘要，历史从约 41230 减少到 6870 tokens）

好的，到目前为止查到的有：……
```

学完今天，你会：

- 说出截断、清理工具输出、写入文件、摘要压缩各自的代价
- 把旧的工具输出换成一行说明，同时保持历史的结构合法
- 把大结果写进文件，上下文里只放引用
- 写一个结构化的摘要提示词，用模型压缩对话
- 用一组埋下的事实，量化地测出压缩丢了什么

## 四种办法和它们的代价

| 办法 | 怎么做 | 丢掉了什么 | 要调用模型吗 |
|---|---|---|---|
| 截断（第 15 天） | 整轮删掉最旧的对话 | 那几轮的一切 | 不用 |
| 清理工具输出 | 旧的工具结果换成一行说明，调用本身留着 | 结果的原文，但可以重新获取 | 不用 |
| 写入文件 | 大结果存进文件，上下文里只留开头 | 什么都没丢，只是要多读一次 | 不用 |
| 摘要压缩 | 模型把旧的对话写成摘要 | 摘要没写进去的细节，而且很难预料是哪些 | 要，还要花钱 |

所以顺序是：能不压缩就不压缩；能用便宜的办法，就不用贵的。

还有一个代价第 15 天讲过：**每一次改写历史，提示缓存都会失效一次。** 不管是清理、压缩还是截断，改写以后的那一轮请求，前缀从 system prompt 之后就不同了。所以不要每一轮都「顺手」压缩一点，而是设一个阈值（mini-agent 用窗口的 60%），超过了才做，而且一次做彻底，之后又能稳定命中缓存好几轮。

## 清理旧的工具输出

研究助手的上下文里，最占地方的是工具结果：一个网页几千个 token，一次搜索几百个 token。而且它们大多是**一次性**的：模型读完网页，把要用的信息写进了回答里，原文之后很少再用。

`pruneToolOutputs()` 把较早几轮里的长工具输出换成一行说明：

```text
[已清理的旧工具输出：原来有 6382 个字符。需要的话重新调用工具]
```

几个细节：

- **工具调用本身留着。** assistant 消息里的 `tool_calls` 不动，模型还知道自己当时调用了 `fetch_page`、打开的是哪个网址，需要时可以原样再调一次
- **tool 消息本身也留着，只换内容。** 第 15 天说过，工具调用和结果必须成对出现。删掉 tool 消息，接口会报错
- **最近几轮不动。** 模型刚读过的东西，很可能下一步还要用。默认保留最近 2 轮
- **短的不动。** 「已写入 result.txt（25 字节）」这样的结果，清理了也省不了几个 token，还丢了信息
- **不改原来的数组。** 返回新的消息数组，出错时会话还能保持原样

这个办法很有效。在一次读了七八个网页的研究里，清理以后，历史常常能缩小一大半，而且一次模型调用都不用。

## 大结果写入文件

清理是事后的补救，更好的是**一开始就不把大结果全放进上下文**。`offloadLargeResults()` 包装一组工具：结果超过 4000 个字符时，把完整的结果写进工作目录的 `.context/results/` 里，交给模型的只有开头一段和文件的位置：

```text
# 潮汐协议 3.0 发布
潮汐协议 3.0 于 2026 年 3 月 14 日发布……（开头 800 个字符）
……
（结果太长，共 23517 个字符，完整内容已保存到 .context/results/fetch_page-1793625952098-3.md。需要后面的内容时，用 read_file 读这个文件）
```

这个思路有一个名字：**把文件系统当作外部记忆**。上下文窗口很小但模型能直接看到，文件系统很大但要用工具去读。重要的、量大的东西放在文件里，上下文里只放「它在哪里」的引用。Claude Code、Manus 这些生产级的 Agent 都大量使用这种做法：长的命令输出、网页、中间结果都写进文件，计划和待办也写进文件，随时可以读回来。

它和第 11 天的分页是互补的：分页适合工具自己就能翻页的情况（`read_article`、`fetch_page`），写入文件适合任何工具，包括 MCP 服务器的工具，它们的结果长短你控制不了。

注意 `read_file` 一次最多读 20000 个字符（第 5 天），更长的文件只能读到开头。给 `read_file` 加上 `offset` 参数，留作今天的小实验。

## 摘要压缩

清理和写入文件以后还是太长，就只能请模型帮忙：把较早的几轮对话写成一份摘要。

`compactHistory()` 的做法：

1. 按轮分组，最近几轮（默认 2 轮）原样保留
2. 更早的几轮写成一份对话记录（`formatTranscript()`）：「用户：……」「助手：……」「助手调用了工具 fetch_page，参数 ……」「工具结果：……」，太长的工具结果截短，摘要不需要逐字的原文
3. 用一个专门的提示词（`SUMMARY_PROMPT`）调用模型，生成摘要
4. 换成 `[system, 摘要, 确认, 最近几轮]`

摘要放在一条 user 消息里，后面跟一条 assistant 消息「好的，我已经了解之前的进展」，这样消息还是一问一答地交替。有的接口不接受连续两条 user 消息，或者会把它们合并，加一条确认最稳妥。

### 摘要提示词怎么写

摘要最常见的问题是**概括得太狠**：「用户查了一些关于潮汐协议的资料，得到了一些数据。」读起来通顺，但端口号、日期、负责人全没了，之后的工作完全用不上。

所以 `SUMMARY_PROMPT` 做了几件事：

- **先说清楚后果**：原来的对话会被删掉，之后只能依靠这份摘要
- **规定结构**：用户的目标、已经确认的事实、做过的事和决定、还没完成的事。结构让模型逐项检查，不容易漏
- **明确要求保留原样的东西**：数字、日期、名字、网址、文件路径原样保留，注明来源编号
- **失败的尝试也要写**：不然压缩以后，模型会把已经证明走不通的路再走一遍

压缩可以用一个更便宜的模型来做（`CompactConfig.model`），但不要太弱：摘要的质量决定了之后所有工作的质量。

### 压缩会出错

生成摘要是一次模型调用，会遇到第 9 天的所有问题：超时、限流、网络错误。还有一种特别的情况：模型返回了一个空的摘要。这时必须报错，**绝不能用一份空摘要替换掉原来的对话**，否则之前的一切都没了。会话里的 `compact()` 在出错时什么都不改，这一轮抛出错误，用户可以再试一次，和第 10 天「出错的一轮不记进历史」是同一个原则。

还要注意，摘要会被反复压缩：第一次压缩产生的摘要，在下一次压缩时也属于「较早的对话」，会和新的内容一起再压缩一遍。信息每压缩一次就可能丢一点，压缩的次数越多，越早的细节越模糊。真正需要长期记住的东西，应该写进文件或者记忆里（第 19 天），而不是指望它在一次次压缩里幸存。

## 怎么测出压缩丢了什么

压缩的效果不能靠感觉。今天的办法很直接：

1. 在对话里**埋下几个关键事实**：项目代号「蓝鲸-7」、负责人「老周」、端口「7443」、上线日期「2026-03-14」、配置文件「tide-config.yaml」
2. 让对话超过阈值，触发压缩
3. 用 `factRetention()` 检查压缩以后的历史里，这些事实还在不在，算出保留的比例
4. 再问模型这些事实，看它答不答得上来

事实要选**必须原样出现的片段**：数字、名字、网址。「用户想要一份通俗的报告」这种意思层面的信息，没法用字符串匹配来检查，要用第 31 天讲的「让模型当评委」来判断。

e2e 测试要求至少保留 80% 的事实。真实模型每次写的摘要都不一样，偶尔丢一个是正常的。如果经常丢，就去改 `SUMMARY_PROMPT`，再跑一遍，比较前后的保留率。这又是第 11 天的思路：改动之前先想好怎么衡量。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 上下文快满了就让模型写摘要 | 摘要最贵、丢得最多。先清理工具输出、把大结果写进文件 |
| 清理工具输出就是删掉 tool 消息 | 删掉会让工具调用没有结果，接口直接报错。只换内容 |
| 每一轮都压缩一点，上下文最省 | 每次改写历史缓存都会失效。超过阈值才做，一次做彻底 |
| 摘要写得越简洁越好 | 简洁的摘要往往丢了数字和名字。要规定结构，明确要求原样保留 |
| 摘要失败了，先用空的顶上 | 绝不能。出错时历史保持原样，这一轮报错 |
| 压缩几次都没关系 | 每压缩一次就丢一点。要长期记住的东西写进文件或记忆 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说「不要修改传进来的数组」 | 直接改了 `message.content`，应该创建一个新的消息对象 |
| 测试说「工具调用要留着」 | 清理时把 assistant 消息的 `tool_calls` 也删了 |
| 测试说「要写出文件的相对路径」 | 结果里写的是绝对路径，或者没有写路径 |
| 写文件时报 `ENOENT` | 没有先建 `.context/results/` 目录 |
| 测试说「最近一轮不压缩」 | `compactHistory` 把所有的轮都交给了模型 |
| 测试说期望 rejects，结果 resolves | 空摘要没有报错 |
| 测试说「写摘要的用量也算进会话」 | 压缩那次调用的 `usage` 没有加进会话 |

## 小实验

- 读几个长网页，看看 `.context/results/` 里多了什么，再让模型「读一下刚才那个网页的后半部分」
- 给 `read_file` 加上 `offset` 和 `limit` 参数，让模型能读写入文件的大结果的任意部分
- 把 `SUMMARY_PROMPT` 改成一句「总结一下这段对话」，用 e2e 测试比较前后的事实保留率
- 用一个便宜的模型写摘要（`CompactConfig.model`），比较摘要的质量和花费
- 连续压缩五次，看看第一轮埋下的事实还剩多少
- `/compact` 之后马上看 `/cost`，体会一下压缩那一轮缓存失效的代价

## 小结

- 上下文快满时，按代价从小到大：清理工具输出 → 写入文件 → 摘要压缩，截断是最后的手段
- 清理只换 tool 消息的内容，调用和结构都留着；最近几轮和短的结果不动
- 大结果写进文件，上下文里只放开头和位置，文件系统就是外部记忆
- 摘要用结构化的提示词，要求原样保留数字、名字、网址，失败的尝试也要写
- 压缩出错时历史保持原样；每次改写都会让缓存失效一次，超过阈值才做
- 埋下事实、压缩、检查保留率：用数字衡量压缩丢了什么
