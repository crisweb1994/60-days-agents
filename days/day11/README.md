# 第 11 天：工具设计

> 最后核对：2026-11-02

第一阶段，你写出了一个会用工具的 Agent。从今天起进入第二阶段：给它好用的工具和恰到好处的上下文，把它变成一个研究助手。

先从工具本身说起。同一个模型、同一个任务，换一套工具，成功率可以差得很远。今天你会拿到一套「设计糟糕」的文献库工具，找出它的毛病，再写一套改好的版本，最后用一组小任务测出改前改后的成功率。

学完今天，你会：

- 站在模型的角度看工具：它能看到什么、看不到什么
- 给工具起名字、写描述、设计参数，让模型一看就知道怎么用
- 让工具返回精简、结构化的结果，长内容分页而不是悄悄截断
- 写出能引导模型自己改正的错误信息
- 用一组小任务量化比较两套工具的好坏

## 模型怎么「看」工具

第 5 天你已经知道，工具交给模型的只有三样东西：名字、描述、参数的 JSON Schema。模型看不到你的代码，看不到数据库长什么样，也不知道你写这个工具时心里想的是什么。它能用的，只有这几行文字，和每次调用之后拿回来的结果。

所以设计工具，其实是在给一个很聪明、但对你的系统一无所知的新同事写说明书。这个新同事有几个特点：

- **会认真读每一个字**，但不会追问。描述里没写清楚的，它只能猜
- **记性有限**。工具的结果会一直留在上下文里，每多一个没用的字段，后面每一轮都要多花 token，也多一分干扰
- **会照着结果的样子往下做**。结果里给的是数字 ID，它就用数字 ID；结果里说「用 page=2 读下一页」，它就会去读下一页

还要记住：工具定义本身也占上下文。每个请求都要带上全部工具的定义，二十个工具、每个描述几百字，就是几千个 token。工具定义放在请求的最前面，一般能命中提示缓存（第 15 天细讲），但它占掉的窗口是实打实的。

打开 [tools/library-bad.ts](exercise/tools/library-bad.ts)，看看这套工具在模型眼里是什么样子：

```json
{ "name": "query", "description": "查询数据", "parameters": { "q": { "type": "string" }, "t": { "type": "string" } } }
{ "name": "lookup", "description": "查找", "parameters": { "id": { "type": "number" } } }
{ "name": "fetch_doc", "description": "获取文档", "parameters": { "docId": { "type": "string" } } }
```

查询什么数据？`t` 该填什么？`lookup` 和 `fetch_doc` 有什么区别？模型一概不知道。

## 名字和描述

**名字**用「动词 + 对象」，一眼看出它做什么：`search_articles`、`read_article`，而不是 `query`、`get`、`data`。工具多了以后，给同一类工具加上相同的前缀（比如 `github_create_issue`、`github_list_issues`），模型更容易分清楚它们属于哪个系统。各家对名字的格式有限制，稳妥的写法是只用字母、数字、下划线和连字符，不超过 64 个字符。

**描述**要回答模型最关心的几个问题：

1. 这个工具做什么，返回什么
2. 什么时候该用，什么时候不该用，和别的工具怎么配合
3. 参数怎么填，最好给一两个例子

比较一下：

```text
改前：查询数据
改后：在文献库里搜索文章。关键词会匹配标题、摘要、作者和标签，多个关键词用空格分开，要全部匹配。
     返回每篇文章的 slug、标题、作者、年份和摘要；要看全文，再用 read_article。
     例子：{"query":"错误信息"}、{"query":"林澈"}、{"query":"","tag":"evaluation","year_from":2025}
```

描述也不是越长越好。关键信息放在最前面，不相关的背景不要写。一个实用的检验办法：把工具定义拿给一个没看过代码的同事，问他会怎么调用。他会犹豫的地方，模型也会犹豫。

## 参数设计

参数是模型最容易出错的地方。几条经验：

- **能用枚举就不用自由字符串。** `tag` 写成 `z.enum([...])`，可选的值直接出现在 JSON Schema 里，模型不用猜
- **用有意义的标识符。** 数字 ID 和 UUID 很容易抄错一位，而且抄错以后可能正好指向另一个真实存在的对象，错误很难发现。`three-part-errors` 这样的短名字抄错了，往往对不上任何对象，工具可以直接报错并给出建议
- **给出合理的默认值。** `limit` 默认 5、`page` 默认 1，模型大多数时候不用管它们。注意一个坑：zod 的 `z.toJSONSchema()` 默认按「校验之后的输出」转换，带 `.default()` 的参数在输出里一定有值，于是被标成了必填。今天的 `toToolDefinition()` 改成了 `z.toJSONSchema(schema, { io: 'input' })`，按「模型要填的输入」转换，有默认值的参数就是可选的
- **写清楚格式和单位。** 日期是 `2025-03-01` 还是时间戳？金额是元还是分？写在参数的 `describe()` 里
- **不要让模型填它不知道的东西。** 比如内部的 bucket 名字、用户 ID。这些应该由你的代码填，不要做成参数
- **参数尽量少，结构尽量平。** 嵌套很深的对象，模型更容易漏掉字段

改后的 `search_articles` 有四个参数，只有 `query` 必填；`read_article` 两个参数，只有 `slug` 必填。

## 返回对模型友好的结果

设计糟糕的 `query` 会把整条数据库记录原样返回：`_rev`、`indexed_at`、`storage`、`acl`，还有全文。搜一次就是几千个字符，其中大部分模型用不上。这些内容会一直留在上下文里，后面每一轮都要为它付费，而且无关的信息越多，模型越容易被干扰、抓错重点。

改后的结果长这样：

```text
共找到 3 篇：
- tool-overlap｜工具职责重叠带来的选择困难｜周以宁、韩松｜2025｜当两个工具的职责有 50% 以上的重叠时……
- mcp-in-production｜MCP 服务器上线一年的教训｜韩松｜2026｜总结了运营 14 个 MCP 服务器一年的经验……
- pagination-for-agents｜分页：给 Agent 的长文本阅读方式｜韩松、唐果｜2024｜与其截断长文本，不如分页返回……
```

几个要点：

- **只留模型用得到的字段。** 后续调用要用的标识符（slug）一定要留，人能读懂的名字（标题、作者）也要留
- **格式前后一致。** 每篇一行，字段顺序固定，模型很快就能学会怎么读。用 JSON 还是用文本行都可以，关键是精简和一致
- **告诉模型结果是不是完整的。** 「共找到 8 篇，只显示了前 2 篇」，模型就知道还有更多，需要时可以调大 `limit`
- **什么都没找到也要说清楚。** 返回空字符串或者 `[]`，模型分不清是没有结果，还是工具出了问题。不如直接建议它换个关键词、去掉筛选条件

### 截断还是分页

第 5 天的 `truncate()` 会在结果太长时截断，并注明总长度。这比悄悄截断好得多，但后面的内容就再也拿不到了。设计糟糕的 `fetch_doc` 更糟：只返回前 500 个字符，一个字也不提，模型会以为自己已经读完了全文。

对于本来就需要读完的长内容，更好的办法是**分页**：每次返回一页，末尾写明「第 1/4 页。用 page=2 读下一页」。模型需要时会接着读，不需要时就停下，不会白白把全文塞进上下文。今天你要写的 `paginate()` 会尽量在换行处分页，不把一行字切成两半。

另一种常见的做法是给工具加一个 `detail` 参数，让模型选择要简要的结果还是详细的结果。原则都一样：**默认给少的，需要时再给多的。**

## 能引导模型自我修正的错误信息

第 5 天说过，工具出错也是一种结果，要交回模型。今天再进一步：错误信息要写得让模型**一次就能改对**。一条好的错误信息回答三个问题：

1. 发生了什么：没有 slug 为 `three-part-error` 的文章
2. 为什么：可能是抄错了
3. 下一步怎么做：你是不是想找 `three-part-errors`？不确定的话，先用 `search_articles` 搜索

对比一下设计糟糕的版本：`工具执行出错：404`。模型只能瞎猜，换一个 ID 再试，或者干脆放弃。

今天在 `tool.ts` 里做两处通用的改进，所有工具都受益：

- **工具名叫错了**：用编辑距离找出最像的那个工具，提示「你是不是想用 search_articles？」。模型叫错工具名，多半是单复数、大小写、下划线和连字符这类小差别
- **参数不对**：zod 的错误信息说明了哪里不对，再附上这个工具每个参数的要求（类型、必填还是可选、说明），模型对照着改一次就能对

```text
参数不符合要求：
✖ 无效输入：期望 string，实际接收 数字
  → at query

search_articles 的参数：
- query（字符串，必填）：关键词，比如「分页」「韩松」。只按标签或年份筛选时填空字符串
- tag（"context" 或 "errors" 或 "evaluation" 或 "mcp" 或 "tools"，可选）：只看带这个标签的文章
……
```

提示也要有分寸：差得太远的「你是不是想用」只会误导模型。今天的规则是编辑距离不超过名字长度的一半才提示。

## 工具数量与职责重叠

工具不是越多越好。每多一个工具，模型每一步都要多做一次选择，而选择越多，选错的机会越大。最常见的问题是**职责重叠**：`lookup` 和 `fetch_doc` 都是「按编号拿一篇文章」，一个返回整条记录，一个返回前 500 字。模型不知道该用哪个，有时候用这个，有时候用那个，结果时好时坏。

几条经验：

- **一个工具做一件完整的事。** 两个工具之间的边界，要能用一句话说清楚：`search_articles` 找文章，`read_article` 读全文
- **按任务设计，而不是按接口设计。** 不要把后端的每个接口都包成一个工具。如果用户的任务总是「先查空闲时间、再建日程」，一个 `schedule_meeting` 工具比 `list_events` 加 `create_event` 好用得多
- **工具多到几十个时，考虑按需加载。** 先给模型一个「查找工具」的工具，或者按任务类型只挂一部分工具。第 13 天接入 MCP 服务器以后，你会很快遇到这个问题

## 怎么知道改好了没有

改了工具，感觉更好用了，但感觉不算数。今天的 `bench.ts` 用一组小任务来量化：

- 每个任务有一个问题和一个判断函数，只检查回答里有没有关键信息
- 同一个任务跑几次，因为真实模型每次的表现不一样
- 统计成功率、平均步数、平均输入 token：成功率高了，步数和 token 也少了，才说明是真的改好了

[data/tasks.ts](exercise/data/tasks.ts) 里的四个任务，每一个都针对一种毛病：按作者搜索（参数含义不清）、读完长文（悄悄截断）、找到文章读出结论（ID 和职责重叠）、筛选再计数（结果臃肿）。答案都只在这个虚构的文献库里，模型不可能事先知道。

这是一个最简单的评估。第 31 天会正式讲评估：怎么建评估集、怎么判分、怎么放进 CI。今天先体会它的核心思想：**改动之前先想好怎么衡量。**

## 常见误解

| 误解 | 实际上 |
|---|---|
| 工具返回的信息越全越好 | 每个多余的字段都要在后面每一轮付费，还会干扰模型。只留它用得到的 |
| 描述写得越长，模型越懂 | 关键信息放前面，不相关的背景不写。太长的描述会把要点淹没 |
| 截断时注明了总长度就够了 | 模型知道后面还有，却拿不到。需要读完的内容应该分页 |
| 错误信息给人看的，简短就行 | 错误信息主要是给模型看的，要说清楚下一步怎么做 |
| 把每个后端接口都包成工具最灵活 | 工具越多越容易选错。按任务设计，一个工具做一件完整的事 |
| 跑一次就能看出哪套工具好 | 真实模型每次的表现不同，同一个任务要跑多次再比较 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说「不区分大小写，- 当成 _」 | `closest` 比较之前没有把名字统一成小写、把 `-` 换成 `_` |
| `closest('send_email', …)` 期望 undefined | 没有设上限：差得太远的名字也给了提示 |
| `describeParameters` 的某一行对不上 | 可选参数写成了必填（没看 `required`），或者枚举参数没用 `typeName` |
| 测试说「被切断了」 | 分页时固定按 `pageSize` 切，没有找换行 |
| 测试说「被截断的回答不算」 | `runBench` 只看了 `check`，没有先看 `status` 是不是 `completed` |
| 测试说「出错的那次不计入步数和 token 的平均」 | `runAgent` 出错时也往平均值里放了 0 |

## 小结

- 模型只能看到工具的名字、描述和参数 schema，以及每次调用的结果。设计工具就是给它写说明书
- 名字用「动词 + 对象」；描述说清做什么、什么时候用、怎么填，给出例子
- 参数用枚举、有意义的标识符和合理的默认值；不要让模型填它不知道的东西
- 结果只留有用的字段、格式一致、说明是否完整；长内容分页，不要悄悄截断
- 错误信息说清发生了什么、为什么、下一步怎么做
- 工具按任务设计，职责不重叠；改动之前先想好怎么衡量
