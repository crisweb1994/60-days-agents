## 关键词检索：BM25

BM25 是搜索引擎用了几十年的打分公式。它的直觉很简单：

- 查询里的词在这一块里**出现得越多**，分数越高，但有上限：出现 10 次不会比 3 次重要太多（参数 `k1`）
- 这个词在所有块里**越少见**，分量越重：「网关」每篇文档都有，没什么区分度；「熔断」只有一篇有，命中它就说明很相关（IDF）
- 块**越长**，每次出现的分量越轻：一篇万字长文里出现一次「证书」，不如一句话里出现一次（参数 `b`）

```text
score = Σ idf(词) × tf × (k1 + 1) / (tf + k1 × (1 − b + b × 块长 / 平均块长))
```

中文要先分词。`Intl.Segmenter` 是 JavaScript 自带的分词器，背后是 ICU 的词典，「向量检索和关键词检索」会切成「向量 | 检索 | 和 | 关键 | 词 | 检索」。英文按单词切，`TIDE_E2077` 和 `handshake.retries` 这种带下划线、点的会保持完整，这对搜编号和配置项正好合适。代价是搜 `handshake` 匹配不到 `handshake.retries`，这正是混合检索要解决的：一种检索漏掉的，另一种补上。

| | 向量检索 | 关键词检索 |
|---|---|---|
| 擅长 | 换了说法的问题：「半夜出事了」→「应急」「回滚」 | 精确的名字、编号、配置项、命令 |
| 不擅长 | 编号、代码、生僻的专有名词 | 同义词、换了说法的问题 |
| 要 embedding 吗 | 要，建索引和查询都要 | 不要 |
| 能解释吗 | 很难说清为什么相似 | 能：因为命中了这几个词 |

## 混合检索：RRF

两种检索各取一份排名，怎么合在一起？直接把分数相加不行：余弦相似度在 0 到 1 之间，BM25 的分数可以是 15，尺度完全不同。

**RRF**（Reciprocal Rank Fusion）只看名次：每个结果在每份排名里得 `1 / (k + 名次)` 分，加起来排序。

```text
向量：  [a, b, c]       a 得 1/61，b 得 1/62，c 得 1/63
关键词：[b, d]          b 得 1/61，d 得 1/62
融合：  b（1/62 + 1/61） > a（1/61） > d（1/62） > c（1/63）
```

在两份排名里都靠前的，总分最高；只在一份里出现的，也有机会。`k` 一般取 60，它让排名第 1 和第 10 的差距不至于太大。RRF 简单、不用调参、效果稳定，是混合检索最常用的融合方法。

`createRetriever()` 把三种方式放在一起：`vector`、`keyword`、`hybrid`。混合时，每种各取 k 的 3 倍作为候选，融合以后再取前 k 个。

## 重排

第一轮检索为了快，用的都是很粗的办法：向量的夹角、词的计数。**重排**是第二轮：从第一轮里多取一些候选（比如 20 个），用一个更准但更慢的办法重新排序，只留最好的几个。

两种做法：

- **专门的重排模型**：把问题和每一段资料**放在一起**读，直接判断相关程度。它比 embedding 准，因为 embedding 是问题和资料各自独立地变成向量，从来没有「同时看两者」。不少服务提供格式相近的 `/rerank` 接口，`createAPIReranker()` 按这种格式写的。具体的服务和模型见 [docs/models.md](../../docs/models.md)
- **让对话模型来排**：把问题和编号的资料发给模型，让它输出 `{"ranking":[3,1,2]}`。不需要额外的服务，但更贵更慢

让对话模型输出 JSON，要准备好它不守规矩：在 JSON 前后加几句话、包在代码块里、给出不存在的编号、重复的编号。`applyRanking()` 逐一处理这些情况。最重要的是：**解析失败时退回原来的顺序。** 重排是锦上添花，不能因为它出错，用户就什么都搜不到。

## 查询改写

用户的问题常常不是好的检索词：

- 太口语：「凌晨线上出故障了，我该先做什么？」文档里写的是「半夜被叫醒怎么办」「回滚」
- 带着指代：「它的端口是多少？」检索不知道「它」是谁
- 一个问题问了几件事：「部署和配置分别要注意什么？」

`rewriteQuery()` 让模型先把问题改写成两三个检索词，每个分别检索，再用 RRF 融合（`multiQuerySearch()`）。原来的问题总是保留在第一个，改写失败时就只用它。

改写多一次模型调用，会慢一点、贵一点。它对口语化的问题帮助很大，对本来就写得很精确的问题帮助不大。

## 把检索交给 Agent

到这里，检索还是一个**固定的流程**：拿到问题 → 检索 → 把结果放进上下文 → 回答。这就是经典的 RAG。它的问题是：检索只有一次，查什么由程序决定。第一次没查到，就没有第二次；问题需要查两个地方，它只会查一个。

**Agentic Search** 把检索做成工具，交给 Agent：

| 工具 | 用途 |
|---|---|
| `search_docs` | 按意思和关键词找段落，可以选检索方式 |
| `grep_docs` | 逐行查找精确的字符串，返回路径和行号 |
| `read_doc` | 读整篇文档，看一段话的上下文 |

Agent 可以先 `search_docs` 看看大概在哪，发现是错误码，再 `grep_docs` 精确地找，最后 `read_doc` 读完整的处理办法。第一次没找到，它会换个说法再查。这就是第 1 天说的 Agent 的核心：**模型决定下一步做什么。**

工具的描述要写清楚三个工具的分工（第 11 天），尤其是什么时候用 `grep_docs`：「找精确的错误码、配置项、命令，用 grep_docs 更准」。检索到的文档也登记成来源（`doc:guide/config.md`），回答时可以用 `[编号]` 引用，和网页一样，第 20 天会把它们合在一起。

两种方式不是非此即彼。固定流程的 RAG 更快、更便宜、更可预测，适合「每个问题都要查文档」的客服场景；Agentic Search 更灵活，适合问题五花八门、需要多步查找的研究场景。也可以结合：先固定地检索一次，把结果放进动态信息（第 15 天），同时也给 Agent 检索工具，不够再查。

### 什么时候 grep 比向量检索更好用

Claude Code 这类编程 Agent 找代码，主要靠的不是向量检索，而是 grep 和读文件。原因是：

- **代码里全是精确的名字。** 函数名、变量名、错误信息，要的就是一字不差
- **代码的结构很清楚。** 目录、文件名本身就是很好的索引，Agent 可以像人一样「先看目录，再打开文件」
- **没有索引就不会过时。** 代码一直在改，向量索引要不停地重建；grep 每次都读最新的文件
- **结果可以解释。** 「在 config.ts 第 42 行找到」，比「相似度 0.73」好理解得多

所以选择取决于你的数据：结构清楚、用词精确的（代码、配置、结构化的技术文档），grep 加读文件常常就够了；用词多样、量很大、结构松散的（笔记、聊天记录、客服知识库），向量和混合检索更有优势。今天的三个工具都给了 Agent，让它自己挑。

## 评估检索

改了切分、换了 embedding 模型、加了重排，效果到底变好了没有？需要一个问答集和几个指标。

[data/qa.ts](data/qa.ts) 有 8 个问题，每个都知道答案在哪篇文档的哪一节，还标了类型：用文档里原词的、换了说法的、问精确编号的。指标有两个：

- **recall@k**：答案所在的块出现在前 k 个结果里的比例。检索的第一要务是「找得到」，排第三也比找不到强
- **MRR**（Mean Reciprocal Rank）：答案排第几，取倒数再平均。排第一得 1 分，第二得 0.5 分，前 k 个里没有得 0 分。它衡量「找得多靠前」

按类型分开统计尤其有用：你会清楚地看到向量检索在「编号」上失分，关键词检索在「换说法」上失分，混合检索两边都不差。

这两个指标只看检索，不用调用对话模型，跑起来又快又便宜，适合频繁地比较。检索找到了，模型也不一定答对，所以 e2e 测试还会让 Agent 用 `search_docs` 真正回答这 8 个问题，检查答案。第 31 天会把这些做成正式的评估流程。

8 个问题当然太少，只能看出明显的差别。你自己的项目，至少准备几十个真实用户会问的问题。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 有了向量检索，关键词检索就过时了 | 精确的名字和编号，关键词检索更准。生产系统大多是混合的 |
| 两种分数归一化以后相加就行 | 分数的分布差别很大，按名次融合（RRF）更稳 |
| 重排失败就报错 | 重排是锦上添花，失败时退回原来的顺序 |
| RAG 就是「检索一次再回答」 | 把检索做成工具，Agent 可以查多次、换方式、换说法 |
| 找代码也该用向量检索 | 代码里全是精确的名字，grep 加读文件常常更好 |
| 检索效果看几个例子就知道了 | 用问答集算 recall@k 和 MRR，按问题类型分开看 |

## 常见错误

| 报错 | 原因 |
|---|---|
| `tokenize` 的结果里有空格和标点 | 没有判断 `isWordLike` |
| 测试说「每块都有的词分数很低」 | 没有乘 IDF，或者 IDF 算反了 |
| 测试说期望 `['short', 'long']` | 没有做长度归一化 |
| RRF 的分数是 1/61，期望 1/62 + 1/61 | 名次从 0 开始算了，或者同一块的分数没有加起来 |
| 测试说期望 `['b', 'd']` | `applyRanking` 没有跳过字符串 `"1"` 或者小数 `1.5` |
| `search_docs` 的结果没有编号 | 没有用 `label(hit, i)` |
| MRR 比期望的大 | 排在第 k 名之后的也算进去了，应该只看前 k 个 |

## 小结

- BM25 认精确的词，向量检索懂意思，两者互补
- 混合检索用 RRF 按名次融合，简单稳定
- 重排用更准的模型给候选重新排序；失败时退回原来的顺序
- 查询改写把口语化、有指代的问题变成好的检索词
- 把检索做成工具，Agent 可以多次、多种方式地查；结构清楚、用词精确的资料，grep 加读文件常常最好用
- 用 recall@k 和 MRR 评估检索，按问题类型分开看
