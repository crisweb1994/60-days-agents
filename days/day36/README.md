# 第 36 天：成本与延迟

> 最后核对：2026-11-07

研究助手一次深度研究要几毛钱、跑好几分钟。一个人用无所谓；一百个人每天用十次，账单和等待都会变成问题。今天把成本和延迟当成两个要管理的指标：先算清楚钱和时间花在哪，再一样一样地省；省完以后用第 33 天的评估确认分数没有掉；最后给每个任务、每个用户设上限，防止一次失控的运行烧掉一个月的预算。

```text
$ node days/day36/solution/eval/optimize.ts --tags web,docs
……
| 评分器 | 基线 | 本次 | 变化 | 回归 | 修好 |
|---|---|---|---|---|---|
| facts | 82% | 82% | 0 个百分点 | 1 | 1 |
……
| 平均每条的花费 | 0.0214 元 | 0.0089 元 |
| 耗时中位数 | 11.2 秒 | 6.4 秒 |

成本降低了 58%
```

学完今天，你会：

- 把一次运行的成本按步骤分解，找到最值得优化的地方
- 用提示缓存、按难度选模型、压缩工具输出、批处理这几种手段降成本
- 测量首字延迟和总耗时，知道哪些手段能缩短真实的等待、哪些只是缩短感觉上的等待
- 给任务和用户设预算上限，预算不够就不再调用模型
- 用评估证明省下的钱没有以牺牲质量为代价

## 先量，再省

第 34 天的 trace 和第 30 天的分步用量已经告诉了我们钱花在哪。一次典型的深度研究：

```text
| 步骤 | 输入 tokens | 输出 tokens | 花费 | 占比 |
|---|---|---|---|---|
| subagents | 48200 | 2600 | 0.1172 元 | 72% |
| verify | 9100 | 640 | 0.0233 元 | 14% |
| report | 6200 | 900 | 0.0196 元 | 12% |
| plan | 420 | 60 | 0.0013 元 | 1% |
```

（`costBreakdown`，单价是示意的 2 元和 8 元每百万 token。）

几个规律几乎总是成立：

- **输入 token 远多于输出**。Agent 每一步都要把整个历史、工具定义、读到的网页再发一遍。省钱首先是省输入
- **调研是大头**。几个子 Agent，每个都带着自己的 system prompt、工具定义和读到的网页
- **输出单价更高**。输出通常是输入的几倍价格，啰嗦的回答、长长的思考都很贵

所以优化的顺序是：先看占比最大的那一步，再看它的输入里都是什么。

## 降成本的几种手段

| 手段 | 省的是 | 代价 | 研究助手里怎么做 |
|---|---|---|---|
| 提示缓存 | 重复的输入前缀 | 几乎没有，要保持前缀稳定 | 系统提示和工具定义不变，日期放在用户消息里（第 15 天） |
| 按难度选模型 | 单价 | 简单的问题可能答得差一点 | 路由（第 22 天）；子 Agent 用便宜的模型（`subModel`） |
| 压缩工具输出 | 输入 | 可能漏掉信息，要多翻页 | `pageSize` 调小；大结果写进文件（第 16 天） |
| 减少步数 | 输入（每一步都重发历史） | 复杂的问题可能查不完 | `maxSteps`、`subagentSteps` |
| 批处理 | 单价（常见的是半价） | 要等几个小时 | 离线评估、模型评审 |
| 控制输出 | 输出 | 回答可能太简略 | prompt 里要求精简；限制 `maxTokens` |

### 提示缓存

大多数模型服务会自动缓存请求的**前缀**：两次请求的开头一模一样，重复的部分按更低的价格计费，也更快。DeepSeek、通义千问、Kimi 等都有这类机制，计费方式各不相同；Anthropic 协议需要在请求里显式标出缓存的位置（`cache_control`），课程的适配器还没有加，可以作为练习。具体以各家的文档为准。

要让缓存命中，前缀必须稳定。第 15 天就是这样设计的：system prompt 和工具定义放在最前面、每次都一样；日期、记忆这些会变的东西放在用户消息里。第 28 天按需检索工具时，新的工具追加在后面，前面的工具定义不变。

`cacheSavings` 算缓存省了多少钱；第 15 天的 `firstDifference` 帮你找出两次请求从哪里开始不一样，也就是缓存为什么没命中。并行的子 Agent 共用同一个 system prompt 和工具定义，这部分前缀天然可以缓存。

### 按难度选模型

第 33 天的横评很可能告诉你：便宜的模型在单个事实的查找上和贵的差不多，在多步推理和「资料里没有答案」的问题上差得多。那就分开用：

- 第 22 天的路由：简单的问题交给便宜的模型
- 深度研究的子 Agent 只负责一个具体的子问题，可以用便宜的模型；规划和写报告用好的模型
- 不要把第 35 天的降级链当成按难度选模型：降级链在「这家出错了」时换，解决的是可用性；便宜的模型答错了不会报错，降级链察觉不到。哪类问题交给哪个模型，要靠评估来定

### 压缩工具输出

网页原文往往是输入里最大的一块。今天给研究助手加了一个旋钮 `pageSize`：`fetch_page` 每页给模型多少字，默认 4000。调成 2000，每读一个网页少一半的输入，代价是有时要多翻一页。第 16 天的 `offloadLargeResults` 把超大的结果写进文件、只给开头，也是同一个思路。

### 批处理

不着急要结果的请求，比如离线评估、给评估结果打分，可以用批处理接口：把请求打包成一个 JSONL 文件交上去，服务方在空闲时处理，一般 24 小时内给结果。[batch.ts](exercise/batch.ts) 实现了 OpenAI 定下、多家兼容的格式：

```text
toBatchJSONL → POST /files（purpose=batch） → POST /batches → 轮询 GET /batches/{id} → 下载 output_file_id → parseBatchOutput
```

比如通义千问提供 OpenAI 兼容的批处理接口，文档写明按实时调用价格的 50% 计费。其他各家是否支持、怎么计费，要查各自的文档。结果文件里的顺序不保证和请求一样，所以每个请求要有自己的 `custom_id`。

Agent 循环本身没法用批处理：每一步都依赖上一步的结果。适合批处理的是**互相独立、不着急**的一大批请求：第 32 天的模型评审给 200 条回答打分，就是典型的例子。

## 延迟：真实的和感觉上的

延迟有两个数字：

- **首字延迟**（TTFT）：从发出请求到看到第一个字
- **总耗时**：到回答完整结束

`measureLatency` 两个都记。它们的优化手段不一样：

| 手段 | 缩短的是 |
|---|---|
| 并行（第 22、25 天） | 总耗时：从「加起来」变成「最慢的那个」 |
| 更小、更快的模型 | 两者都缩短 |
| 更短的输入 | 首字延迟：模型要先读完输入 |
| 提示缓存 | 首字延迟：缓存的部分不用重新处理 |
| 少几步 | 总耗时 |
| 流式输出（第 3 天） | **感觉上的**等待：用户马上看到字在出来 |
| 显示进度 | **感觉上的**等待：「正在查子问题 2/3」比空白的转圈好得多 |

后两种不减少真实的时间，但对体验的影响往往最大。深度研究要跑几分钟，如果屏幕上一直是空白，用户会以为它卡死了；如果能看到计划、看到每个子问题查完、看到「正在写报告」，同样的几分钟就可以接受。第 30 天的 `onEvent` 就是为此设计的，第 44 天的 Web 界面会把它做成实时的进度条。

看延迟也要看 P90（第 33 天）：中位数 6 秒、P90 40 秒，说明有一部分请求出了问题（限流后重试、某个网页很慢），要去 trace 里找原因。

## 预算：给每个任务和用户设上限

Agent 的成本是不确定的：一个问题可能 3 步就答完，也可能因为一个奇怪的网页在里面绕 15 步。一次运行失控，就可能花掉平时一百次的钱。所以要有硬性的上限。

[cost.ts](exercise/cost.ts)：

```ts
const user = createBudget({ name: '用户 u1 今天', limit: 2, price });           // 每个用户每天 2 元
const task = createBudget({ name: '这个任务', limit: 0.5, price, parent: user }); // 每个任务 0.5 元
const model = withBudget(createModel(...), task);
```

- **调用之前先估**：用第 15 天的 token 估算，加上假设的输出，算出这次大概要多少钱。不够就不调用，抛出 `BudgetExceededError`
- **调用之后按实际记账**，而且记到每一级上级
- **预算用完不是模型的错误**：不会被重试，也不会触发故障转移。重试只会再撞一次上限；换一个模型也是花钱
- `createLedger` 按用户、按天记账。它存在内存里，进程重启就清零了；第五阶段做多用户时要存进数据库

预算用完以后怎么办？和第 35 天的期限一样：能交出部分结果就交出部分结果，并且告诉用户为什么停了。

## 省钱要拿评估来验证

每一种省钱的手段都可能悄悄地降低质量：便宜的模型更爱编，更短的分页漏掉了关键的那一句，更少的步数让多跳的问题查不完。所以**省钱的改动和改 prompt 一样，要过第 33 天的门禁**。

[eval/optimize.ts](exercise/eval/optimize.ts) 在同一个评估集上跑两种配置，用第 33 天的 `compareRecords` 比较分数和花费：

```ts
const configs = [
  { name: 'baseline', model: main },
  { name: 'lean', model: cheap, pageSize: 2000, maxSteps: 8 },
];
```

`costReduction` 算出成本降了多少：两边都配了单价就比较花费，没有单价就按加权的 token 估算（输出按 4 倍算）。目标是**成本降 30% 以上、分数不明显下降**。一次只改一个旋钮更好：你会知道每一种手段各省了多少、各掉了多少分。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 省钱就是换便宜的模型 | 先看钱花在哪。多半是输入太多：历史、工具定义、网页原文 |
| 输出 token 少，不用管 | 输出单价更高；思考 token 也算输出 |
| 缓存是服务商的事 | 前缀不稳定，缓存就命中不了。这是你的 prompt 结构决定的 |
| 批处理什么都能用 | Agent 循环每一步依赖上一步，用不了。适合独立、不着急的一大批请求 |
| 流式输出让回答更快 | 总耗时不变，缩短的是感觉上的等待。但感觉上的等待很重要 |
| 预算用完了重试一下 | 预算不是故障。重试和换模型都是继续花钱 |
| 省了 50% 的钱，赚了 | 要看评估分数掉了多少。掉了 10 个百分点，可能得不偿失 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说「上级也要记上」 | `charge` 只加了自己，没有让 `parent` 也记 |
| 测试说「自己的预算够，但上级不够了，说的是上级」 | `check` 只检查了自己 |
| 测试说「超了就不该调用模型」 | `withBudget` 先调用、后检查 |
| 测试里预算用完以后备用模型被调用了 | `BudgetExceededError` 被当成了可以换模型的错误。它的 `classifyError` 是 unknown，不在换模型的种类里 |
| `costBreakdown` 测试说占比的和应该是 1 | 用每一步的花费除以了别的东西，或者没有排序 |
| `cacheSavings` 测试说 saved 不对 | `withoutCache` 要把 `cachedTokens` 当作 0 再算，不是把输入减掉缓存的部分 |
| 测试说「调用方的 onText 照样能收到」 | 包装里只记了时间，没有转给原来的回调 |
| 测试说只调用了工具时不应该有 `ttftMs` | 没收到字的时候写成了 `ttftMs: undefined` |
| 批处理测试说 body 不应该带 stream | 自己拼了请求体，没有用 `toRequestBody` |

## 小实验

- 一次只改一个旋钮（只换模型、只改 `pageSize`、只改 `maxSteps`），各跑一遍 `optimize.ts`，填一张「省了多少、掉了多少」的表
- 连续问同一个问题两次，看第二次的 `cachedTokens`；再把 `RESEARCH_PROMPT` 改成每次带上当前时间，看命中率怎么变
- 用 `measureLatency` 包住深度研究的模型，比较规划、子 Agent、写报告三类调用的首字延迟
- 用批处理接口（如果你的模型服务支持）给第 32 天的人工标注跑一遍模型评审，和实时调用比较花费和等待的时间
- 给 `/deep` 设一个 0.05 元的任务预算，看它在哪一步停下

## 小结

- 先量，再省：按步骤分解成本，输入通常是大头，调研通常是最贵的一步
- 降成本的手段：保持前缀稳定让缓存命中、按难度选模型、压缩工具输出、减少步数、离线任务用批处理、控制输出
- 延迟分首字延迟和总耗时；流式输出和进度展示缩短的是感觉上的等待，同样重要
- 给任务和用户设硬性的预算上限：调用前先估，调用后记账，预算用完不重试、不换模型
- 省钱的改动也要过评估的门禁：成本降了、分数没掉，才算省成功
