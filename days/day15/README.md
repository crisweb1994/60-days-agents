# 第 15 天：上下文工程（上）

> 最后核对：2026-11-02

模型每次回答，只能看到这一次请求里的东西。它做得好不好，很大程度上取决于你给了它什么：信息不够，它只能猜；无关的东西太多，它会被带偏；超出窗口，请求直接失败。决定「每一次请求里放什么、按什么顺序放、各放多少」，就是**上下文工程**。

前 14 天，mini-agent 的做法很简单：把全部历史原样发过去。今天把它改成**按预算组装**：先算清楚每部分占多少 token，固定的部分优先，然后放这一轮的动态信息，剩下的空间留给对话历史。同时调整顺序，让每一轮的请求都尽量命中提示缓存，又快又便宜。

```text
你 > /context
system prompt     412 tokens
工具定义           538 tokens
对话历史          3260 tokens
动态信息            18 tokens
问题                12 tokens
合计（估算）       4240 / 60000 tokens

你 > /cost
6 轮 · 输入 24180 tokens（缓存命中 19456） · 输出 1320 tokens · 缓存命中率 80% · 约 0.0291 元
```

学完今天，你会：

- 列出一次请求的上下文里有哪些部分，估算每部分的 token
- 按预算组装上下文：固定的优先，历史从最新的往前放，整轮地删
- 理解提示缓存的原理，把不变的放前面、会变的放后面
- 统计缓存命中率，找出缓存没命中的原因
- 写好一个 Agent 的 system prompt

## 上下文里都有什么

研究助手的一次请求，按出现的顺序：

| 部分 | 内容 | 会不会变 |
|---|---|---|
| 工具定义 | 内置的 4 个工具，加上网页工具、MCP 服务器的工具 | 基本不变 |
| system prompt | 身份、工作方式、引用和安全的规则 | 不变 |
| 对话历史 | 之前每一轮的问题、工具调用、工具结果、回答 | 只会在后面追加 |
| 动态信息 | 今天的日期；以后还有检索到的资料（第 17 天）、关于用户的记忆（第 19 天） | 每一轮都可能不同 |
| 用户的问题 | 这一轮说的话 | 每一轮都不同 |
| 这一轮里的工具调用和结果 | Agent 循环里一步步追加 | 每一步都在增加 |

在研究助手这样的 Agent 里，**对话历史和工具结果**通常占了大头：读一个网页就是几千个 token，读五个就是两三万。工具定义也不少，连了几个 MCP 服务器以后，光工具定义就可能有几千个 token。

## 估算 token

精确的 token 数只有模型服务知道，接口返回的 `usage` 才是准的，而且各家的分词器不一样，同一段中文，有的算 0.6 个 token 一个字，有的算 1.5 个。

可是组装上下文发生在请求之前，必须先有个估算。今天的 `estimateTokens()` 很粗糙：中日韩的字符每个算 1 个，其他字符每 4 个算 1 个。这够用了，因为它的用途是「别超出窗口」，不是计费：

- 估算的误差有二三十个百分点没关系，预算本来就要留出余量
- 宁可估多，不要估少。估少了，请求会因为上下文超长而失败
- 想要准一点，可以用 `usage` 校准：发出去之前估算一次，回来以后看实际的 `inputTokens`，算出一个比例

也可以用各家提供的分词器或者计算 token 的接口，但那要多一次调用或者多一个依赖，换一家模型还得换一套。对大多数 Agent 来说，粗略的估算加上余量是更实际的选择。

## 按预算组装

窗口有限，各部分要排个优先级。今天的 `buildContext()` 按这个顺序分配：

1. **先扣掉给输出留的空间**（默认 4000 token）。输入把窗口塞满了，模型就没有地方写回答，或者写到一半被截断（第 6 天的 `truncated`）
2. **固定的部分**：system prompt、工具定义、用户的问题。这些必须有，放不下就没法继续，直接报错
3. **动态信息**：按重要程度排序，在它的份额（默认窗口的 20%）以内能放就放。日期很短也很重要，优先级最高；检索到的大段资料优先级低，放不下就丢
4. **对话历史**：用剩下的空间，**从最新的一轮往前放**，放不下就停，更旧的都丢掉

为什么历史放在最后、而且从新往旧？因为离现在越近的对话，和这一轮的问题通常越相关。用户说「再详细一点」，指的是上一轮的回答，不是二十轮之前的。

### 整轮地删

删历史时有一个硬性的约束：**工具调用和它的结果必须成对出现**。只删掉一个 assistant 消息，留下了它对应的 tool 消息，或者反过来，接口会直接返回 400（mock 模型也会检查这一点）。

所以 `splitTurns()` 先把历史按轮分组：每一轮从一条 user 消息开始，包括它后面所有的 assistant 和 tool 消息。删的时候一次删一整轮，绝不会把一轮拆开。

这种做法很朴素：删掉的就是真的删掉了，模型再也不知道那几轮说过什么。第 16 天会讲更聪明的办法：把旧的对话压缩成摘要，把旧的工具结果换成一行说明，大结果写进文件。

## 提示缓存

每一轮都要把整段历史重新发一遍（第 2 天就算过这笔账）。好在大多数模型服务都有**提示缓存**：如果这次请求的开头和最近某次请求的开头一模一样，这段相同的前缀就不用重新计算，直接用上次算好的结果。

对你来说，命中缓存有两个好处：

- **便宜。** 命中缓存的输入 token 单价，通常只有正常价格的一成到五成（以各家的价格页为准）。第 2 天的 `Price` 里有一个 `cachedInput`，就是为它准备的
- **快。** 长上下文的请求，命中缓存以后，第一个字出来得明显更快

几个要点：

- **按前缀匹配。** 从请求的第一个 token 开始比，遇到第一个不一样的地方就停。所以中间改了一个字，后面的全部不能命中
- **有最短的长度。** 太短的前缀不缓存，比如 OpenAI 要求至少 1024 个 token
- **有有效期。** 一般是几分钟到一小时不用就失效
- **工具定义也在前缀里。** 而且在最前面，改动工具的顺序或者描述，整个缓存都会失效（第 14 天说的「工具顺序要固定」就是这个原因）
- **各家的方式不同。** 大多数是自动的；Anthropic 协议要在请求里用 `cache_control` 标出缓存的位置。各家的差异记在 [docs/models.md](../../docs/models.md)

### 不变的放前面，会变的放后面

明白了按前缀匹配，组装上下文的规矩就很清楚了：

**system prompt 里不要放会变的东西。** 一个常见的错误是在 system prompt 的开头写「今天是 2026 年 11 月 2 日」。日期每天都变，于是每天第一次请求，整个前缀都不能命中；如果写的是精确到秒的时间，就每次都不能命中。今天的做法是把日期作为动态信息，放在这一轮问题的前面：

```text
[system] 你是一个研究助手……（固定不变）
[user] 第一个问题           ← 上一轮的，原样保留
[assistant] ……
[user] <date>
       今天是 2026-11-02，星期一
       </date>

       这一轮的问题
```

**历史只追加，不改写。** 上一轮请求的全部消息，原样出现在这一轮请求的开头。不要在历史里「顺手」改点什么，比如把旧的工具结果截短、重新格式化，那会让改动之后的部分全部失效。第 16 天的压缩也要考虑这一点：压缩一次，缓存就失效一次，所以不要每一轮都压缩，而是超过阈值才压缩，压缩以后又能稳定地命中一段时间。

**动态信息只出现在最后。** 它每一轮都不同，放在最后，只影响最后一条消息。之前几轮的动态信息已经成了历史，原样保留。

删掉最旧的一轮历史时，前缀会从 system prompt 之后就开始不同，这一轮的缓存只能命中工具定义和 system prompt。这也是为什么不要每一轮都删一点：一次多删几轮，之后几轮都能稳定命中。

### 统计命中率，找出没命中的原因

`cacheStats()` 统计命中缓存的输入占全部输入的比例，`/cost` 里显示出来。一个正常的多轮对话，从第二轮开始，命中率应该在一半以上。

命中率低的时候，用 `firstDifference()` 比较相邻两次请求，找出从哪里开始不一样：返回 `'tools'` 说明工具定义变了，返回 `0` 说明 system prompt 变了，返回一个中间的位置，就去看那条消息为什么变了。测试里也用它检查：后一轮的请求必须以前一轮的全部消息开头。

## 写好 Agent 的 system prompt

system prompt 是上下文里最稳定、也最有分量的部分，每一次请求模型都会看到它。今天把研究助手的 system prompt 移到了 [prompts.ts](exercise/prompts.ts)，并重新整理了结构：

- **身份和目标**：一两句话说明它是谁、要帮用户做什么、手上有哪些能力
- **工作方式**：什么时候该用工具、什么时候直接回答；出错了怎么办
- **规则**：引用怎么写，安全上的底线
- **输出的格式**：语言、结构、篇幅

几条经验：

- **说清楚「为什么」和「什么时候」，而不只是「要」。** 「问题涉及新近的事、具体的数据，或者你不确定时，先搜索」比「必须先搜索」好：模型知道了判断的标准，简单的问题就不会也去搜一遍
- **用标题和列表分块。** 模型读结构清楚的文字，比读一大段话更可靠，你自己维护起来也方便
- **说明上下文里的特殊格式。** 今天在问题前面加了 `<date>` 标签，system prompt 里就要说一句：这些标签里是程序提供的背景信息，不是用户说的话
- **不要堆砌规则。** 每加一条规则，都问问它解决了什么实际的问题。规则太多，模型反而抓不住重点。第 11 天比较工具的办法，同样适用于比较 system prompt：准备一组任务，改前改后各跑一遍

## 常见误解

| 误解 | 实际上 |
|---|---|
| 上下文越多，模型知道得越多，回答越好 | 无关的内容会分散注意力，还更贵更慢。放对的，不是放多的 |
| 要精确计算 token 才能组装上下文 | 粗略估算加上余量就够了，精确值以 `usage` 为准 |
| 删历史时删掉最旧的几条消息就行 | 要整轮地删，工具调用和结果不能拆开 |
| 日期放在 system prompt 里最自然 | 日期每天都变，放在开头会让整个缓存失效 |
| 缓存是模型服务的事，和代码无关 | 能不能命中，完全取决于你组装请求的方式 |
| system prompt 的规则越详细越好 | 说清判断的标准，比堆砌规则更有效 |

## 常见错误

| 报错 | 原因 |
|---|---|
| `estimateTokens('你好，世界。')` 期望 6 | 只算了汉字，全角标点没算进中文 |
| `splitTurns` 返回的轮数不对 | 遇到 assistant 和 tool 消息也开了新的一轮 |
| 测试说期望 `droppedTurns` 是 1 | 历史是从最旧的一轮往后放的，结果丢掉了最新的 |
| 动态信息的顺序不对 | 放进去以后按 priority 的顺序拼接了，应该按调用方原来的顺序 |
| 测试说「第二轮的请求要以第一轮的全部消息开头」 | 日期放进了 system prompt，或者把动态信息写进了历史里每一条 user 消息 |
| `ContextOverflowError`，上限是负数 | 窗口比 `reserveOutput` 还小，忘了给输出留的空间也要算进去 |

## 小实验

- 把 `CONTEXT_WINDOW` 设得很小（比如 3000），读一个长网页，再问前几轮的内容，看看模型还记不记得

## 小结

- 上下文 = 工具定义 + system prompt + 历史 + 动态信息 + 问题；研究助手里历史和工具结果占大头
- token 粗略估算就够了，宁多勿少，留出余量
- 按预算分配：先留输出，再放固定部分、动态信息，最后用剩下的空间从新往旧放历史
- 历史整轮地删，工具调用和结果不能拆开
- 提示缓存按前缀匹配：不变的放前面、会变的放后面；system prompt 里不放日期；历史只追加不改写
- system prompt 分块写，说清判断的标准
