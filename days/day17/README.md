# 第 17 天：RAG（上）：向量检索

> 最后核对：2026-11-02

研究助手能上网，能读网页，但它读不了你自己的资料：公司的产品文档、你多年的读书笔记、一个项目的全部设计文档。几百份文档不可能全部塞进上下文；就算塞得下，模型也会被大量无关的内容淹没（第 15 天）。

**RAG**（Retrieval-Augmented Generation，检索增强生成）的思路是：先从文档里**找出和问题相关的几段**，只把这几段放进上下文，再让模型回答。今天实现检索这一半：给一个文档目录建索引，问一个问题，返回最相关的 k 段。

```bash
$ node days/day17/exercise/rag/indexer.ts index ~/docs
新增 4 篇，更新 0 篇，删除 0 篇，跳过 0 篇；这次做了 9 块的 embedding，索引里一共 9 块

$ node days/day17/exercise/rag/indexer.ts search ~/docs "服务上线之前需要做哪些准备？"
[1] guide/deploy.md · 部署 > 上线前的检查（相似度 0.71）
上线之前要确认证书没有过期，并且在 #release 频道里通知值班的人。
……
```

注意问题里说的是「服务上线之前需要做哪些准备」，文档里写的是「上线前的检查」「确认证书没有过期」，字面上几乎没有重合，却能找到。这就是向量检索的本事。

学完今天，你会：

- 理解 embedding 是什么，为什么意思相近的文字向量也相近
- 比较几种 embedding 模型的选择，包括国产的和本地的
- 设计切分策略：按标题分节、按段落合并、太长的硬切并留重叠
- 写一个暴力检索的向量库，知道什么时候该换成专门的向量库
- 增量地建索引，只给改过的文档重新做 embedding
- 用元数据过滤检索的范围

## embedding：把意思变成坐标

**embedding 模型**把一段文字变成一个向量，也就是一串数字，比如 1024 个浮点数。它在训练时学会了一件事：**意思相近的文字，向量的方向也相近**。

「怎么把服务部署上线？」和「上线的步骤是什么」意思差不多，它们的向量夹角很小；「番茄炒蛋怎么做」和它们毫无关系，夹角就很大。衡量方向是否接近，用**余弦相似度**：两个向量夹角的余弦，1 表示方向完全相同，0 表示无关，越大越相似。

```ts
cosine(a, b) = (a · b) / (|a| × |b|)
```

检索的过程就是：

1. **建索引**（一次性）：把文档切成块，每块做 embedding，存起来
2. **检索**（每次提问）：把问题做 embedding，和每一块的向量算相似度，取最高的 k 块

这里有一个常被忽略的要求：**建索引和检索必须用同一个 embedding 模型。** 不同模型的向量就像不同的坐标系，维数可能都不一样，放在一起比较毫无意义。所以向量库的文件里记下了建索引用的模型，换了模型，旧的索引直接作废，要重建。

### mock 模型的 embedding 不懂意思

离线测试用的 mock 模型也提供了 `/embeddings` 接口，但它不懂意思：它把文字切成词和相邻的两个字，哈希到 256 个维度上。字面上共用的词越多，相似度越高，「上线」和「部署」在它看来毫无关系。这足够测试切分、存储、增量索引这些流程，测不了「换一种说法也能找到」。那要靠 e2e 测试，用真实的 embedding 模型。

## embedding 模型怎么选

不是每家模型服务都提供 embedding。通义千问、智谱、硅基流动（提供多种开源模型）、OpenAI 都有 OpenAI 兼容的 `/embeddings` 接口；也有服务（比如 DeepSeek）的文档里没有 embedding 接口，这时可以另选一家，只用它做 embedding。本地的 Ollama 也能跑开源的 embedding 模型，不花钱，数据不出电脑。具体的模型名和接口地址见 [docs/models.md](../../docs/models.md)。

选的时候看：

| 考虑 | 说明 |
|---|---|
| 中文效果 | 有的模型主要用英文训练，中文效果差很多。用你自己的文档和问题试一试最准 |
| 维数 | 维数越高，表达能力越强，但存储和计算也越多。有的模型支持指定维数（`dimensions`） |
| 最长输入 | 超出的部分会被截断或者报错，这决定了块的上限 |
| 价格 | embedding 比对话便宜得多，但文档多了也是一笔钱，所以要增量索引 |
| 能不能本地跑 | 文档涉及隐私时，本地模型是唯一的选择 |
| 单次条数上限 | 各家不同，客户端要分批发送 |

配置单独放在 `EMBEDDING_*` 里：

```bash
EMBEDDING_BASE_URL=   # 不填就用 OPENAI_BASE_URL
EMBEDDING_API_KEY=    # 不填就用 OPENAI_API_KEY
EMBEDDING_MODEL=      # 必须填
```

[rag/embeddings.ts](exercise/rag/embeddings.ts) 的客户端做两件小事：**分批**（每批 16 条，一次发太多会超出接口的上限，一次一条又太慢）和**按 `index` 排序**（接口返回的 `data` 不保证和输入一样的顺序）。空文字直接报错，因为接口也会拒绝它。

## 切分：检索的单位是块

为什么不直接给整篇文档做 embedding？

- **一篇文档讲很多事。** 部署文档里既有 Docker，又有上线检查，整篇的向量是所有内容的「平均」，和哪个具体的问题都不够像
- **检索出来要放进上下文。** 一篇几万字的文档，检索到了也放不下
- **embedding 模型有输入上限。** 太长的部分会被截掉

但块也不能太小：一句「运行下面的命令」，脱离了上下文，谁也不知道在说什么。

[rag/chunk.ts](exercise/rag/chunk.ts) 的策略是**按结构切**：

1. **按标题分节。** Markdown 的标题就是作者给的结构，同一节通常在讲同一件事。每一节记下它的标题路径，比如「部署 > 用 Docker 部署」。代码块里以 `#` 开头的行是注释，不是标题
2. **一节太长，按段落合并。** 段落尽量完整地放进同一块，放不下就开始新的一块，每块不超过 800 个字符
3. **一个段落都太长，硬切，并留重叠。** 相邻两块重叠 100 个字符，免得一句话正好被切成两半，两边都检索不到

还有一个小技巧：做 embedding 的时候，不只用块的正文，还在前面加上**文档路径和标题路径**（`embeddingText()`）。「运行 docker run -p 7443:7443 tide/gateway」加上「guide/deploy.md · 部署 > 用 Docker 部署」，向量就能反映它真正的主题。这种做法有时叫「上下文化的块」。

块的大小没有标准答案，几百到一两千个字符都常见。块小，检索更精确，但每块的信息少，要多取几块；块大则相反。最好的办法是用你自己的问题集试，第 18 天会搭一个对比检索效果的评估。

## 向量库

[rag/vector-store.ts](exercise/rag/vector-store.ts) 是一个最简单的向量库：所有的块和向量都在内存里，检索时把问题的向量和**每一块**都算一遍相似度，排序取前 k 个。这叫**暴力检索**（brute-force）。

听起来很笨，但算一下：一万块、每块 1024 维，一次检索是一千万次乘加，JavaScript 里几毫秒就算完了。个人的笔记、一个产品的文档，通常就是几千到几万块，完全够用。它保存成一个 JSON 文件，不需要装任何数据库。

规模再大（几十万、上百万块），就该换专门的向量库了。它们用**近似最近邻**（ANN）索引，比如 HNSW，不再和每一块比较，而是沿着一张预先建好的图快速找到最近的几个，用一点点准确率换来快得多的速度：

| 选择 | 特点 |
|---|---|
| [sqlite-vec](https://github.com/asg017/sqlite-vec) | SQLite 的扩展，一个文件就是一个库，适合本地和单机 |
| [LanceDB](https://lancedb.github.io/lancedb/) | 嵌入式的向量库，有 Node.js 的包，适合较大的本地数据 |
| pgvector | PostgreSQL 的扩展。第五阶段做多用户的 Web 应用时换成它，向量和业务数据放在同一个数据库里 |

不管用哪个，接口都差不多：存入（向量 + 元数据），按向量检索 top-k，按元数据过滤。今天的 `VectorStore` 就是这个接口的最小实现，以后换成别的，调用它的代码不用改。

### 元数据过滤

每一块都带着元数据：路径、标题。检索时可以先过滤，只在一部分块里找：

```ts
store.search(vector, { k: 5, filter: (chunk) => chunk.path.startsWith('guide/') });
```

用户说「在部署文档里找」，或者你知道某类问题只和某个目录相关，过滤能大大减少无关的结果。真实的系统里，元数据还常常有日期、作者、标签、权限，比如「只检索这个用户有权限看的文档」，这在第 46 天做多用户时非常重要。

`minScore` 是另一种过滤：相似度低于某个值的不要。但要小心，相似度的绝对值在不同的模型之间差别很大，有的模型相关的结果在 0.8 以上，有的在 0.5 左右。阈值要用你的模型、你的数据试出来。

## 增量建索引

文档会改。每改一个字就把几百篇文档全部重新做一遍 embedding，又慢又贵。[rag/indexer.ts](exercise/rag/indexer.ts) 记下每篇文档内容的哈希（SHA-256），再建索引时：

- 哈希没变：跳过
- 哈希变了：删掉这篇文档的旧块，切出新块，重新做 embedding
- 目录里已经没有的文档：从索引里删掉

有一个顺序上的细节：**先算新的向量，再删旧的块。** embedding 是网络请求，随时可能失败。如果先删后算，算到一半出错，这篇文档就从索引里消失了；先算后删，出错时索引里还是旧的、能用的内容。这和第 10 天「出错的一轮不记进历史」、第 16 天「摘要失败时历史保持原样」是同一个原则：**失败时，保持上一个好的状态。**

## 常见误解

| 误解 | 实际上 |
|---|---|
| 向量检索能找到所有相关的内容 | 它擅长找意思相近的，不擅长精确的名字、编号、代码。第 18 天会讲关键词检索 |
| 块越大，信息越完整，检索越好 | 块大了向量会变模糊，检索出来还占地方 |
| 换个 embedding 模型，接着用旧索引就行 | 不同模型的向量不能比较，必须重建 |
| 一定要用专门的向量数据库 | 几万块以内，暴力检索又快又简单 |
| 相似度 0.5 以上就是相关的 | 相似度的范围因模型而异，阈值要自己试 |
| 文档改了就全部重建索引 | 用哈希判断，只重建改过的 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说期望 `[16, 16, 8]` | 没有分批，或者每批的条数算错了 |
| 测试说期望的向量和实际的对不上 | 没有按 `index` 放回去，直接用了返回的顺序 |
| `splitSections` 的 heading 是「A > B > C」，期望「C」 | 回到上一级标题时，没有把 path 截短 |
| 测试说「代码块里的 # 不是标题」 | 没有跟踪是不是在代码块里 |
| `splitLong` 的最后多了一块很短的 | 最后一块已经到结尾了还继续切 |
| 测试说「零向量不要除以 0」，结果是 NaN | 没有处理长度为 0 的向量 |
| 测试说 embedding 出错后旧内容应该还在 | 先删了旧的块，再做 embedding |

## 小实验

- 把 `maxChars` 改成 200 和 3000，用同样的问题比较检索结果

## 小结

- embedding 把文字变成向量，意思相近的向量方向相近，用余弦相似度衡量
- 建索引和检索必须用同一个模型；换了模型就重建
- 切分按结构：标题分节、段落合并、太长硬切并留重叠；做 embedding 时带上路径和标题
- 几万块以内暴力检索就够了，更大的规模换成用 ANN 索引的向量库
- 元数据过滤缩小检索的范围
- 用哈希增量建索引；先算新向量再删旧块，失败时保持上一个好的状态
