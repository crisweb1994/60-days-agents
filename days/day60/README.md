# 第 60 天：结业

> 最后核对：2026-11-08

60 天前，你写下了第一个 60 行的 Agent：一个模型、一个查术语表的工具、一个循环。今天，你有一个上线的多用户研究助手、一个自己选题、自己评估、自己上线并开源的 Agent 产品，以及讲清楚它们的能力。

最后一天做三件事：**复盘这 60 天、把作品放到作品墙上、想清楚接下来学什么**。

学完今天，你会：

- 写一篇有具体例子的学习复盘
- 把毕业项目整理成作品集，提 PR 加到学员作品墙
- 知道这门课没有覆盖、接下来值得学的方向

## 回头看：六个阶段，一条主线

| 阶段 | 你做出了什么 | 最重要的一句话 |
|---|---|---|
| 一、手写 Agent（1–10） | mini-agent | Agent = 模型 + 工具 + 循环；每一行都可以测试 |
| 二、工具与上下文（11–20） | 研究助手 v1 | Agent 的上限由工具和上下文决定 |
| 三、复杂任务（21–30） | 研究助手 v2 | 能用简单方案就别上 Agent；规划、反思、子 Agent 都有代价 |
| 四、工程化（31–40） | 研究助手服务 | 没有评估，就不知道改了以后是变好还是变坏 |
| 五、框架与产品化（41–50） | 上线的 Web 应用 | demo 和产品之间，隔着后台任务、多用户、部署和运营 |
| 六、毕业项目（51–60） | 你自己的 Agent 产品 | 先写评估，再写代码；达标就停，上线才算完 |

如果只记住一件事，大概是这个：**Agent 工程的核心不是让模型更聪明，而是让系统可衡量**。评估集、trace、成本、成功标准，这些让你能说出「它现在有多好、为什么、下一步改哪里」。

## 复盘

[templates/retro.md](templates/retro.md) 是复盘的模板。几个建议：

- **写具体的例子**，不要写「学到了很多」。「第 37 天我以为把系统提示写严一点就能防注入，红队用例一跑才知道……」比「了解了提示注入」有用得多
- **对照计划和实际**：哪个阶段花的时间远超预期？卡在哪里？这是你下一步最该补的地方
- **写下毕业项目接下来的三件事**：来自第 50 天的试用反馈、第 55 天还没解决的失败、你自己的待办
- 复盘可以公开：写成一篇文章发出去，就是第 57 天说的「让第一批用户找到你」

## 作品集和作品墙

一份 Agent 方向的作品集，比一份「熟悉 LangChain、了解 RAG」的简历有说服力得多。它至少包括：

| 内容 | 来自 |
|---|---|
| 毕业项目的仓库：README 有演示、效果的数字、局限 | 第 57 天 |
| 线上地址 | 第 56 天 |
| 需求说明、设计文档、迭代记录 | 第 51、52、55 天 |
| 一篇文章：你踩过的坑和数字 | 第 57 天 |
| 3 分钟的项目讲述 | 第 59 天 |

然后把它加到这门课的[学员作品墙](../../SHOWCASE.md)。[showcase.ts](exercise/showcase.ts) 先检查格式：

```bash
node days/day60/exercise/showcase.ts --name review-bot --repo https://github.com/你的用户名/review-bot \
  --author 你的用户名 --pitch "给小团队的 PR 审查机器人，少而准" --demo https://你的在线地址
```

检查通过，它会把一行加到 `SHOWCASE.md` 表格的最后。提交、推到你 fork 的仓库、提 PR。作品墙要求项目**已经上线并开源**。

## 接下来学什么

这门课有意没有覆盖的方向（[ROADMAP 附录 B](../../ROADMAP.md)），按和你已有的东西的距离排：

| 方向 | 为什么值得学 | 从哪里接着做 |
|---|---|---|
| 语音 Agent | 实时、打断、延迟以百毫秒计，和文字 Agent 是另一套工程 | 第 3 天的流式、第 44 天的界面 |
| 电脑操作（computer use） | 没有 API 的系统也能操作；感知和安全都更难 | 第 27 天的浏览器、第 38 天的沙箱 |
| 本地与端侧模型 | 隐私、离线、成本；小模型的工具调用能力差很多 | 第 8 天接入 Ollama、第 33 天的横评 |
| Agentic RL 与微调 | 用你的评估集和 trace 训练更适合你的任务的模型 | 第 31–34 天的评估和 trace 就是数据 |
| 更大规模的多 Agent 系统 | 协议（A2A）、长时间运行、Agent 之间的信任 | 第 25、26 天 |

另外两件比任何新方向都重要的事：

- **继续维护你的毕业项目**。回复 issue、按反馈迭代、每次改 prompt 都跑评估。一个维护了半年、有真实用户的小项目，比十个 demo 更能说明你的能力
- **跟上变化，但别追着跑**。模型、框架、协议每个月都在变，这门课的代码也会过时。但评估、可观测性、可靠性、安全、成本这些问题不会消失。新东西出来时，问一句：它解决了这几个问题里的哪一个？

## 常见错误

| 报错 | 原因 |
|---|---|
| 检查的测试少报了 pitch 里的 \| | 只检查了 name；五个字段都要查 |
| 用户名的测试说 a--b 不合法 | GitHub 用户名不能有连续的连字符，也不能以连字符开头或结尾 |
| 字数的测试差了 | 用了 `.length`，要用 `[...文字].length` |
| 读作品墙读出了表头 | 表头的格式和作品的行不一样，ROW 匹配不上；检查正则有没有改松 |
| 查重的测试没报错 | 比较仓库地址时没有去掉末尾的 / 和统一大小写 |
| 加的行跑到了文件末尾 | 要插在以 \| 开头的最后一行后面，不是文件的最后 |

## 小结

- 六个阶段：手写 Agent、工具与上下文、复杂任务、工程化、框架与产品化、毕业项目
- Agent 工程的核心是让系统可衡量：评估、trace、成本、成功标准
- 作品集要有：上线的地址、开源的仓库、效果的数字、写下来的设计和迭代、讲得清的故事
- 接下来：继续维护你的项目；学新东西时，问它解决了评估、可观测性、可靠性、安全、成本里的哪一个

60 天到这里结束。谢谢你一路走到这里。
