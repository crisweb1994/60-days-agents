# 第 19 天：记忆

> 最后核对：2026-11-02

上周你告诉研究助手：「我们用 Kubernetes 部署，回答简短一点。」今天打开一个新的对话，它全忘了。这不奇怪：第 1 天就说过，接口什么都不记，`messages` 就是 Agent 的全部记忆，关掉程序，`messages` 就没了。

今天给它两种跨越会话的能力：

- **长期记忆**：值得长期记住的事（偏好、背景、纠正过的做法）写进一个目录里的 Markdown 文件，每一轮都放进上下文
- **会话的持久化与恢复**：每一轮结束就把对话存下来，关掉程序、换一天，都可以接着聊

```text
你 > 我们用 Kubernetes 部署，以后回答简短一点，记住
✓ remember {"name":"deploy-k8s","type":"project","content":"用户的项目用 Kubernetes 部署"}
✓ remember {"name":"prefers-short-answers","type":"user","content":"用户喜欢简短的回答"}

记住了。

（第二天，新的对话）
你 > 怎么扩容？
在 Kubernetes 里把网关的副本数加一就行，新实例大约 40 秒后开始接收流量。

你 > /sessions
* 20261103-091502-k3f9  2026-11-03 09:15  1 轮  怎么扩容？
  20261102-201133-a7c2  2026-11-02 20:11  6 轮  我们用 Kubernetes 部署，以后回答简短一点…
```

学完今天，你会：

- 分清短期记忆和长期记忆，知道各自放在哪里
- 判断什么该记、什么不该记、什么时候该忘
- 实现一个基于文件的记忆库和三个记忆工具
- 防止敏感信息被写进记忆
- 把会话可靠地存到硬盘，从崩溃中恢复

## 短期记忆和长期记忆

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 是什么 | 这一次对话的历史 | 跨越很多次对话都有用的信息 |
| 存在哪 | `messages`，在内存里 | 文件或数据库 |
| 多大 | 受上下文窗口限制，满了要压缩（第 16 天） | 可以很多，但每次只放一部分进上下文 |
| 谁决定内容 | 自动：每一轮都追加 | 有选择：模型或程序判断哪些值得记 |
| 什么时候消失 | 会话结束 | 过期、被纠正、被要求忘掉 |

第 16 天的压缩，处理的是短期记忆太长的问题。今天的长期记忆，处理的是**跨会话**的问题。两者也有交集：压缩时丢掉的细节，如果重要，应该在丢掉之前写进长期记忆。

## 该记什么

不是什么都值得记。记得越多，每一轮放进上下文的就越多，越贵，也越容易干扰模型（第 15 天）。今天把记忆分成四类，这也是判断「该不该记」的标准：

| 类型 | 是什么 | 例子 |
|---|---|---|
| `user` | 用户是谁、有什么偏好 | 「用户喜欢简短的回答」「用户是后端工程师，不熟悉前端」 |
| `feedback` | 用户纠正过的做法 | 「引用放在句末，不要放在开头」 |
| `project` | 正在做的事、背景和约束 | 「项目用 Kubernetes 部署」「报告 2026-11-06 要交」 |
| `reference` | 外部资源的位置 | 「监控大盘在 grafana.example.com」 |

**不该记**的：

- **一次性的事**：「帮我算一下 1+1」
- **能重新查到的事**：文档里写着的、网上搜得到的、代码里看得到的。记下来反而会过时，查最新的才准
- **敏感信息**：密码、API Key、证件号、银行卡号。见下一节

还有一个细节：**相对的时间要换成绝对的**。用户周一说「下周五交报告」，记成「下周五」，到了下周一再读就错了。`remember` 工具的参数说明里写着：「日期写成绝对日期（2026-11-06），不要写『下周五』」。动态信息里有今天的日期（第 15 天），模型能换算。

## 该什么时候忘

记忆也会过时。三种忘的方式：

- **过期**：有些信息只在一段时间内有用，比如「这周在准备发布」。记的时候设一个有效期（`ttl_days`），到期自动删掉
- **被纠正**：用户说「我们已经从 Docker 换成 Kubernetes 了」，同名的记忆直接更新，而不是新增一条。否则两条矛盾的记忆同时存在，模型不知道该信哪个。所以记忆有一个名字（`deploy-method`），同名就覆盖
- **被要求**：用户说「忘掉我的公司名」，就用 `forget` 删掉。这不只是功能，也是对用户的尊重

## 文件式的记忆

记忆存在一个目录里，一条记忆一个 Markdown 文件，再加一个索引 `MEMORY.md`：

```text
.mini-agent/memory/
  MEMORY.md                    # - [deploy-k8s](deploy-k8s.md)（project）用户的项目用 Kubernetes 部署
  deploy-k8s.md
  prefers-short-answers.md
```

```markdown
---
type: project
created: 2026-11-02T12:11:33.000Z
updated: 2026-11-02T12:11:33.000Z
---

用户的项目用 Kubernetes 部署
```

为什么用文件，而不是数据库？

- **人能直接看、直接改。** 用户想知道 Agent 记住了自己什么，打开目录就能看到；记错了，直接改文件就行。这对建立信任很重要
- **能放进版本管理。** 项目相关的记忆可以和代码一起提交，团队共享
- **足够简单。** 个人用的 Agent，记忆最多几百条，文件完全够用

这和 `AGENTS.md`、`CLAUDE.md` 这类文件是一个思路：一份放在项目里、给 Agent 看的说明。区别在于 `AGENTS.md` 通常是人写给 Agent 的，而今天的记忆主要由 Agent 自己写。很多编程 Agent 两种都有：启动时读取项目里的 `AGENTS.md`，工作中再把学到的东西写进自己的记忆文件。

人手改文件难免改坏。读取时，格式不对的文件跳过，不影响其他的记忆。

### 放进上下文

每一轮开始前，`memorySection()` 把记忆整理成一段动态信息（第 15 天），放在问题前面：

```text
<memory>
你记得的关于用户和项目的事：
- prefers-short-answers（user）：用户喜欢简短的回答
- deploy-k8s（project）：用户的项目用 Kubernetes 部署
</memory>
```

为什么不放在 system prompt 里？因为记忆会变。放在 system prompt 里，每记一条，整个前缀的缓存就失效一次。放在最后的动态信息里，只影响最后一条消息。

记忆多了也放不下。`memorySection()` 按最近更新的顺序放，超出长度的只列出名字，模型需要时用 `recall` 去查。这又是第 16 天「上下文里只放引用」的思路。

## 记忆工具

三个工具，什么时候记、记什么，由模型判断：

| 工具 | 用途 |
|---|---|
| `remember` | 记下一条，同名的更新 |
| `forget` | 忘掉一条 |
| `recall` | 按关键词查找，或者列出全部 |

判断的规则写在 system prompt 里（[prompts.ts](exercise/prompts.ts) 的「记忆」一节）：用户告诉你以后也用得到的信息、或者纠正了你的做法，就记下来，**并告诉用户你记住了**。最后这一点很重要：用户应该知道 Agent 记了什么，不应该在背后悄悄地记。

也可以不让模型判断，而是在每次会话结束时，由程序把对话交给模型，让它总结出值得记住的东西。这样更全面，但更贵，也更容易记下用户不想被记住的东西。两种方式各有取舍，今天用的是更透明的那种。

## 隐私

记忆是**明文存在硬盘上**的，而且会被**放进之后的每一次请求**，发给模型服务。所以敏感信息绝对不能进记忆。

用户说「把我的 API Key 记下来，省得每次输入」，模型可能真的会照做。所以不能只靠 system prompt 里的一句「不要记敏感信息」，`remember()` 在写文件之前还会用正则检查一遍：API Key、令牌、私钥、身份证号、银行卡号、手机号，发现了就拒绝，并告诉模型该怎么回复用户。这是第 12 天讲过的原则：**提示词是建议，代码才是防线。**

正则只能挡住格式固定的东西，挡不住「我的密码是我女儿的生日」。所以还要做到：

- 用户能看到所有的记忆（`/memory`、直接打开目录），能随时删除
- 记忆的目录不要放进公开的仓库
- 多用户的系统里，每个用户的记忆严格隔离（第 46 天）

## 会话的持久化与恢复

长期记忆只记要点。有时候你想要的是**原样接着聊**：昨天研究到一半的问题，今天继续。

[session-store.ts](exercise/session-store.ts) 在每一轮结束时，把整个会话（历史、用量、轮数）存成一个 JSON 文件。`/sessions` 列出保存的会话，`/resume <id>` 恢复，启动时也可以用 `--resume <id>`。

可靠地保存，有几个细节：

**原子地写文件。** 直接覆盖写文件，写到一半程序崩溃了（或者断电了），文件就只剩一半，再也读不出来。正确的做法是先写一个临时文件，写完再**改名**成正式的文件名。改名在操作系统里是原子的：要么是旧文件，要么是新文件，不会有半个。

**坏文件不能拖垮整个列表。** 列出会话时，某个文件坏了就跳过；读取那个会话时，明确地报错，说明是哪个文件。

**修补中断的历史。** 第 10 天的规则是「只有跑完的一轮才记进历史」，所以正常情况下保存的历史都是完整的。但如果程序在执行工具时崩溃了，或者文件是别的版本的程序写的，历史的最后可能有一个没有结果的工具调用。恢复时 `repairHistory()` 给它补上「没有执行：会话在执行工具时中断了」的结果，否则恢复以后的第一个请求就会被接口拒绝。这和第 6 天 `finish()` 补结果是同一件事。

**记下格式的版本。** 文件里有一个 `version` 字段。以后格式变了，读到旧版本的文件可以转换，或者明确地报错，而不是读出一堆错乱的数据。

**id 不能带路径。** 会话的 id 会拼进文件路径，`/resume ../../etc/passwd` 这样的 id 必须拒绝。

恢复的时候，模型用的是**现在**配置的模型，不一定是当时用的那个。历史始终是我们自己的格式（第 8 天），换模型没有问题，只是会提示一下当时用的是哪个。

第 29 天会讲一种更难的恢复：Agent 在后台跑一个长任务，跑到第 37 步时服务器重启了，怎么从第 37 步接着跑，而不是从头再来。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 记得越多，Agent 越懂用户 | 记多了更贵，也更容易被干扰。只记以后真正用得到的 |
| 能查到的东西也记下来，省得再查 | 记下来会过时，查最新的才准 |
| 「下周五」照原样记就行 | 相对时间过几天就错了，要换成绝对日期 |
| 新信息就新增一条记忆 | 被纠正的信息要更新原来那条，否则会有矛盾的记忆 |
| system prompt 里说了不记敏感信息就够了 | 提示词是建议，写文件之前要用代码检查 |
| 直接覆盖写文件就行 | 写到一半崩溃，文件就坏了。先写临时文件再改名 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说期望 `['身份证号']`，结果多了银行卡号 | 银行卡号的正则把身份证号的前 17 位也匹配上了 |
| 日期、端口被当成了手机号 | 手机号的正则前后没有限制不能紧挨着别的数字 |
| 测试说「敏感信息绝不能写进文件」 | 先写了文件，再检查 |
| 更新以后有两条记忆 | 同名的没有覆盖，或者索引里没有去掉旧的那条 |
| 测试说「过期的文件要删掉」 | 过期的只是没放进结果，文件还在 |
| 目录里留下了 `.tmp` 文件 | 写完临时文件没有改名 |
| 测试说期望 `['new', 'old']`，结果报错 | 列出会话时，坏掉的文件让整个函数抛出了错误 |

## 小实验

- 告诉它几件关于你的事，用 `/memory` 看看它记了哪些、没记哪些，是不是你期望的
- 直接用编辑器改一条记忆文件，下一轮问它相关的问题
- 告诉它「我们换成 Docker 部署了」，看看它是更新了原来的记忆，还是新增了一条
- 聊到一半直接关掉终端（不用 `/exit`），再用 `--resume` 恢复
- 让它「记住这周五要开会」，看看它记下的日期对不对，有没有设有效期
- 记二十条记忆，看看 `/context` 里动态信息占了多少

## 小结

- 短期记忆是这次对话的历史，长期记忆是跨会话有用的信息
- 只记以后用得到、又查不到的：偏好、纠正、项目背景、资源位置；相对时间换成绝对日期
- 记忆会过期、会被纠正、会被要求忘掉：设有效期，同名覆盖，提供 `forget`
- 记忆存成人能看、能改的 Markdown 文件，每一轮作为动态信息放进上下文
- 敏感信息在写文件之前就用代码挡住
- 会话每一轮自动保存：原子写入，坏文件跳过，恢复时修补中断的历史
