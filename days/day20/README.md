# 第 20 天：里程碑：研究助手 v1

> 最后核对：2026-11-02

第二阶段的十天，你给 mini-agent 装上了一样又一样的能力：好用的工具、联网搜索、MCP、上下文的预算和压缩、本地文档的检索、记忆。今天把它们组装成第二阶段的成果：**研究助手 v1**。接到一个问题，它会上网查、读来源、翻你的本地文档，带着可以核对的引用作答，还记得你是谁、你在做什么。

```text
研究助手 · openai:my-model · 搜索 bocha · 本地文档 /Users/you/docs · 工作目录 /Users/you/workspace
MCP 服务器：连上了 1/1 个，共 2 个工具

你 > 潮汐协议 3.0 的默认端口改成了多少？我们的部署文档里，上线前要检查什么？
✓ web_search {"query":"潮汐协议 3.0 默认端口"}
✓ fetch_page {"url":"https://tide.example/news/3.0.html"}
✓ search_docs {"query":"上线前的检查"}

潮汐协议 3.0 把默认端口改成了 7443 [1]。按照部署文档，上线之前要确认 TLS 证书没有过期，
在 #release 频道里通知当天值班的人，灰度阶段先放 5% 的流量 [3]。

来源：
[1] 潮汐协议 3.0 发布说明 https://tide.example/news/3.0.html
[3] 本地文档 guide/deploy.md

本轮：输入 9840 tokens（缓存命中 6144） · 输出 186 tokens · 0.0082 元
```

学完今天，你会：

- 把搜索、读网页、文档检索、记忆、MCP 组装成一个研究助手
- 统一网页和本地文档两种来源，回答里用同一套编号引用
- 写一个引用格式的检查器，自动发现不合格的回答
- 用端到端测试验证整条链路

## 组装工具

[research.ts](exercise/research.ts) 的 `createResearchTools()` 按顺序收集所有的工具：内置的、网页、本地文档、记忆、MCP 服务器。有两个要点：

**网页和本地文档共用一个来源登记。** 这样回答里的 `[1]` 可能是一个网页，`[3]` 可能是一份本地文档，编号不会冲突。本地文档的「网址」写成 `doc:guide/deploy.md`，来源列表里显示成「本地文档 guide/deploy.md」。

**名字重复的只留第一个。** 内置的工具放在最前面，所以它们优先。一个 MCP 服务器碰巧也有一个叫 `calculator` 的工具，就不会悄悄地顶替掉内置的那个。第 13 天给 MCP 工具加了前缀，正常情况下不会重名，这里是第二道保险。

最后，所有的工具都包上第 16 天的 `offloadLargeResults()`：不管是哪个工具、哪个 MCP 服务器，结果太长都写进文件。

没有配置的部分就不出现：没有搜索的 Key，就没有 `web_search`（但还能用 `fetch_page` 读给定的网址）；没有 `DOCS_DIR`，就没有本地文档的工具。研究助手照样能用，只是能力少一些。

## 一次研究

`research()` 回答一个问题，是整条链路最清楚的样子：

1. 组装工具
2. 准备动态信息：今天的日期（第 15 天），记住的事（第 19 天），放在问题前面
3. 用研究助手的 system prompt 运行 Agent 循环，最多 15 步：研究常常要搜几次、读几个网页、查几处文档
4. 看这一轮有没有用过查资料的工具，检查引用的格式
5. 在回答后面附上被引用的来源

命令行里的研究助手（[cli.ts](exercise/cli.ts)）走的是同样的流程，只是多了会话：多轮对话、上下文的预算和压缩、每一轮的保存。`research()` 适合写脚本、做批量的评估：

```bash
node days/day20/exercise/research.ts "潮汐协议 3.0 有什么变化？"
```

## 引用检查

研究助手的价值在于**可以核对**：每个结论都能顺着编号找到出处。可是模型并不总是守规矩：它可能忘了标引用，可能编出一个不存在的编号，可能把引用写在句子开头，或者自己在最后写一个来源列表，里面的网址是编的。

[citations.ts](exercise/citations.ts) 的 `checkCitations()` 在每次回答以后自动检查五条规则：

| 规则 | 为什么 |
|---|---|
| 引用的编号都是登记过的来源 | 没登记过的编号，多半是模型编的 |
| 查过资料的回答，至少要有一个引用 | 查了资料却不标出处，用户没法核对 |
| 带具体数字的句子要标明来源 | 数据、日期、版本号是最容易出错、也最需要核对的 |
| 引用写在句子的末尾 | 统一的格式，人读起来、程序检查起来都方便 |
| 不要自己写来源列表 | 来源列表由程序根据编号附上，模型写的网址可能是编的 |

「这一轮有没有查资料」是一个关键的开关。用户说「你好」，模型回答「你好！有什么可以帮你？」，不该因为没有引用而报错。所以只有这一轮用过 `web_search`、`fetch_page`、`search_docs` 这些工具，才要求引用。

「带数字的句子」是一个很粗糙的启发式规则：它会放过没有数字的错误结论，也可能误伤「我找到了 3 篇相关的文档」这样的句子。但它便宜、确定、能放进测试，能抓住大部分最要紧的问题。这正是格式检查的定位：**它只检查格式，不检查内容。** 「这句话是不是真的出自 [1]」，要让模型对照来源逐句核对，那是第 25 天讲反思时要做的引用核查。

检查不通过时，命令行会提醒用户：

```text
默认端口是 7443。

（引用检查：查过资料，但回答里没有任何引用；这句话有具体的数字，但没有标明来源：「默认端口是 7443。」）
```

更进一步，可以把检查的结果交回模型，让它改一遍再交给用户。这是一个「生成 → 检查 → 修正」的循环，第 25 天会正式地做。

## 端到端测试

前十天的测试大多是单元测试：一个函数、一个工具。今天的测试要验证**整条链路**：搜索、读网页、查文档、回答、附上来源、引用检查，一个环节出错，结果就不对。

难点在于外部依赖太多：搜索服务、网页、embedding 模型、对话模型。测试的办法和前几天一样，能换成本地假服务的都换掉：

| 依赖 | mock 模式 | e2e 模式 |
|---|---|---|
| 对话模型 | mock 模型，按脚本回复 | 真实模型 |
| embedding | mock 的 embedding | 真实的 embedding 模型 |
| 搜索服务 | 本地的假服务（第 12 天的那个） | 还是本地的假服务 |
| 网页 | 本地的假网页 | 还是本地的假网页 |
| 本地文档 | `data/docs/` | `data/docs/` |

e2e 模式下，搜索和网页仍然用本地的假服务。这样测试不需要搜索的 Key，不受真实网页变化的影响，而且答案只在假网页里，模型不可能事先知道。e2e 测试问一个需要同时查网页和本地文档的问题，检查：答案里有只能从两边查到的信息；引用里既有网页，也有本地文档；没有编造的编号。

注意 e2e 测试**没有**要求引用检查完全通过：真实模型偶尔会漏掉一个数字的引用，这很正常，测试打印出检查的结果，你自己判断。一个可靠的产品，要靠第 31 天的评估集，统计「引用检查的通过率」这样的指标，看它在一百个问题上的表现，而不是看它在一个问题上是否完美。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 工具越多，研究助手越强 | 工具多了更容易选错。没配置的能力就不加，名字重复的只留一个 |
| 网页和文档各编各的号更清楚 | 编号会冲突，模型和用户都会混淆。共用一个来源登记 |
| 有引用就说明回答是对的 | 格式检查只看格式；内容对不对，要对照来源核查 |
| 闲聊也要检查引用 | 只有查过资料的回答才要求引用 |
| e2e 测试要连真实的搜索和网页才算数 | 外部服务会变、要 Key、答案不可控。用本地的假服务，只把模型换成真的 |
| 一次 e2e 通过就说明质量没问题 | 要在一组问题上统计通过率（第 31 天） |

## 常见错误

| 报错 | 原因 |
|---|---|
| 来源列表里本地文档显示成 `doc:guide/deploy.md` | `formatSourceLine` 没有区分本地文档 |
| 测试说「这句话有具体的数字」的问题没有报出来 | 没有分句，整段检查时只要有一个引用就放过了 |
| 闲聊的回答报了「没有任何引用」 | 没有看 `researched` |
| 测试说「内置的优先」 | MCP 的工具放在了内置工具的前面，或者重复的保留了后一个 |
| 测试说期望 `[3] 本地文档 guide/deploy.md` | 本地文档用了另一个来源登记，编号重新从 1 开始了 |
| 问题前面没有日期或记忆 | 动态信息没有用 `formatQuestion` 放进问题 |

## 第二阶段小结

十天前，mini-agent 只能读写本地的文件。现在它是一个研究助手：

- 工具照着「给模型用」的规矩设计：名字、描述、参数清楚，结果精简，错误能引导改正，长内容分页
- 能上网搜索、读网页，每个来源都有编号，回答带着可以核对的引用
- 能接入任何 MCP 服务器，你自己的数据源也能做成 MCP 服务器给别的 Agent 用
- 上下文按预算组装，不变的放前面命中缓存；长任务里会清理、写入文件、压缩
- 能检索你的本地文档：向量、关键词、混合、重排，或者让 Agent 自己 grep
- 记得你的偏好和项目，关掉再打开也能接着聊
- 每一部分都有测试，用本地的假服务和 mock 模型，大部分不用联网就能跑

它现在还缺什么？它一次只做一件事，一步一步地来：复杂的研究问题，它不会先列一个计划，不会把问题拆开并行地查，写完报告也不会回头检查自己引用得对不对。第三阶段（第 21–30 天）就来解决这些：工作流与 Agent 的取舍、路由与并行、规划、反思、子 Agent、多 Agent 协作、浏览器、Skills 和人在回路，把它变成研究助手 v2。

## 想一想

- 「对比三家搜索 API 的价格和中文效果」这样的问题，有固定的步骤：每家各查一遍，再汇总。这时用固定的工作流好，还是让 Agent 自己决定好？（第 21 天）
- 三家的资料可以同时查。怎么让研究助手并行地做几件事？（第 22 天）
- 研究助手写完回答，能不能自己对照来源检查一遍，发现引用不对就改？（第 25 天）
