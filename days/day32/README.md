# 第 32 天：评分方法

> 最后核对：2026-11-07

昨天的评估只会一种检查：回答里有没有出现期望的事实，结果是对或错。这已经能发现不少问题，但它看不见很多东西：

- 回答写了「18 毫秒」，可它说成是 2.x 的延迟
- 事实全对，但先绕了三段客套话才说到
- 答案对了，可它把同一个搜索调用了五次，花了三倍的钱
- 引用了来源，但引用的是一个不相干的网页

今天把「怎么打分」拆成一个个**评分器**：用代码检查的事实、引用和调用轨迹，用模型评审的回答质量和两两比较。然后回答两个评分本身的问题：模型评审靠不靠得住（和人工标注校准），分数的波动有多大（多次运行看方差）。

```text
$ node days/day32/solution/eval/cli.ts --judge --repeat 3
……
| 评分器 | 平均分 | 通过率 |
|---|---|---|
| facts | 0.86 | 76% |
| citations | 0.91 | 80% |
| trajectory | 0.94 | 88% |
| quality | 0.78 | 64% |

跑了 3 遍，facts 的通过率：76%、72%、80%（标准差 3.3 个百分点）
时对时错的：multi-config-upgrade（1/3）、unanswerable-last-2x（2/3）
```

学完今天，你会：

- 写代码评分器：事实、引用、调用轨迹，并且让分数说清楚扣在哪里
- 写模型评审：评分细则、两两比较，知道它们各自的偏差和对策
- 用人工标注校准评审，看懂一致率和 kappa
- 同一个评估多跑几遍，找出时对时错的用例

## 评分器：一个统一的接口

[graders.ts](exercise/eval/graders.ts) 里每个评分器都是：

```ts
interface Grader {
  name: string;
  grade(c: EvalCase, output: TargetOutput): Score | Promise<Score>;
}
// Score：{ grader, value: 0 到 1, pass, reason }
```

它只看第 31 天存下来的输出，不需要重新跑 Agent。这就是「运行和检查分开」的好处：新写一个评分器，拿以前跑过的结果直接打分。

**分数和通过都要有**。代码评分器都是一组检查：分数是通过的比例，全部通过才算过。分数用来看趋势（从 0.6 涨到 0.8，在变好），通过用来看底线。**理由一定要写**：「0.67」什么都没告诉你，「缺少 42；出现了 15」告诉你该去看哪里。

## 代码评分：能用代码判断的，就别用模型

| 评分器 | 检查什么 | 抓得住的问题 |
|---|---|---|
| `facts` | 期望的事实都出现、禁止的内容没出现、没有答案时说了没查到 | 答错、编造、该说不知道却硬答 |
| `citations` | 引用了该引用的来源、引用格式没有问题、没有答案时不引用来源 | 引用了不相干的网页、编号是编的 |
| `trajectory` | 调用了该调用的工具、顺序对、没有超过次数、没有一模一样的重复调用 | 闲聊也去搜索、原地打转、该算的没用计算器 |

代码评分便宜、快、每次结果都一样，应该是评估的主体。它的局限是只能检查「写得出规则」的东西。

### 调用轨迹：怎么得到答案也重要

最终答案对了，过程可能很糟：搜了五次一样的关键词、闲聊也去查资料、算 499 × 12 靠「心算」。这些问题在最终答案里看不出来，却实实在在地花钱、增加延迟、埋下出错的隐患。

评估集里今天给几条用例加上了轨迹的期望：

```json
{"id": "web-latency", ..., "expected": {"facts": ["18", "42"], "tools": ["web_search", "fetch_page"]}}
{"id": "chat-greeting", ..., "expected": {"maxToolCalls": 0, "forbidden": ["[1]"]}}
```

`tools` 要按顺序出现，但中间可以夹着别的调用（`isSubsequence`）。不要把轨迹写得太死：「必须先 web_search 再 fetch_page，一共恰好两次」会让一个多搜了一次、但答得更好的 Agent 不通过。**检查你真正在乎的约束**，比如「读过网页再回答」「不超过 N 次」，而不是一模一样的步骤。

## 模型评审：判断代码判断不了的

「回答切不切题」「有没有把不确定的说成确定的」，写不出规则，只能让模型来判断。这就是 LLM-as-a-judge。它很有用，但它也是一个模型：会偏、会错、会被回答的长度和语气影响。下面每一个设计都是在对付一种偏差。

### 评分细则：把「好不好」拆成几件能单独判断的事

```ts
export const QUALITY_RUBRIC = [
  { name: '切题', description: '5 分：第一句就直接回答了问题；1 分：答非所问，或者绕了很久才说到' },
  { name: '准确', description: '5 分：和参考答案一致，没有编造……；1 分：关键事实错了，或者编了数字' },
  { name: '诚实', description: '5 分：资料不足的地方明确说了；1 分：把不确定的说成确定的……' },
  { name: '简洁', description: '5 分：没有客套话和重复……；1 分：大段和问题无关的内容' },
];
```

- **一条细则只管一件事**。「整体质量 1 到 10 分」是最差的写法：评审自己也不知道 7 分和 8 分差在哪
- **写清楚两端是什么样**。描述越具体，评审越稳定
- **给评审参考答案**。评审不知道潮汐协议，没有参考答案，它只能凭语气判断「像不像对的」
- **temperature 设成 0**，并且解析失败算 0 分。评审出错不能当成回答好

### 两两比较：比打分更稳

让模型给一个回答打 1 到 5 分，它的标准会飘；但问它「A 和 B 哪个更好」，它判断得准得多。比较两个版本（改 prompt 前后、两个模型）时，两两比较往往比各自打分再比较平均分更可靠。

它有一个出名的毛病：**位置偏差**，评审常常偏向排在前面（或者后面）的那个。对策是交换位置再比一次：

| 第一次（a 在前） | 第二次（b 在前，换算回来） | 结果 |
|---|---|---|
| a 赢 | a 赢 | a 赢 |
| a 赢 | b 赢 | 平局：两次都选了排在前面的，说明它在看位置，不在看内容 |
| 解析不了 | 任何 | 平局 |

两次评审互不依赖，可以同时发出。代价是调用翻倍。

### 其他常见的偏差

| 偏差 | 表现 | 对策 |
|---|---|---|
| 长度偏差 | 更长的回答拿更高的分 | 细则里单独有「简洁」，prompt 里明说不要因为长给高分 |
| 自我偏好 | 评审偏爱和自己同一家模型写的回答 | 评审用另一家的模型；至少要知道有这回事 |
| 放水 | 什么都给 4 分 | 和人工标注校准，看「评审放水」那一格 |
| 被说服 | 回答里写着「这是一个准确的回答」 | 评审的 prompt 把回答当作要评的材料，第 37 天会再讲 |

## 校准：评审和人的判断一致吗

模型评审能不能用，不能凭感觉，要拿人的判断来对照。[judge-labels.jsonl](data/eval/judge-labels.jsonl) 是 12 条人工标注：评估集里几条用例的不同回答，人判断了合不合格。好坏各半，坏的各有毛病：编了数字、张冠李戴、啰嗦、该说没查到却硬答。

`calibrate()` 让评审给这 12 个回答打分，和人的判断比较。两个数字：

- **一致率**：判断一样的比例
- **Cohen's kappa**：扣掉「碰巧一致」以后的一致程度

为什么一致率不够？假设人标的回答 90% 都是好的，一个一律说「好」的评审，一致率就有 90%，可它什么都没判断。kappa 会把这部分扣掉：

```text
kappa = (实际一致率 - 碰巧一致率) / (1 - 碰巧一致率)
碰巧一致率 = 评审说好的比例 × 人说好的比例 + 评审说差的比例 × 人说差的比例
```

一律说好的评审，kappa 是 0。一般认为 kappa 到 0.6 以上算比较一致，0.8 以上很一致，但这只是参考，更重要的是去看**不一致的那几条**：

- 评审说好、人说差（**放水**）：最危险。比如「数字是编的」那条，评审没有参考答案以外的知识，看不出来。对策：细则里写清楚「参考答案之外的数字按编造处理」
- 评审说差、人说好（**太严**）：可能是参考答案写得太窄，或者细则要求了用户并不在乎的东西

12 条只是演示。真正要用评审做决定，至少标 50 到 100 条，而且要由懂这个领域的人来标。标注本身也会暴露问题：你会发现自己对「什么是好回答」也没想清楚，这正是写评分细则之前该想清楚的。

## 方差：分数会自己动

同一个评估集、同一份代码，跑两遍，通过率可能一次 76%、一次 72%。模型的输出本来就不确定，搜索的关键词变一点，读到的网页就不同。

`repeatability()` 把同一个评估跑几遍的结果放在一起看：

- **每遍的通过率、标准差**：标准差是 3 个百分点，那么改动以后从 76% 变成 74%，基本说明不了什么
- **每遍都过**的用例：稳定
- **每遍都不过**的：确定的问题，修它
- **时对时错**的：最值得看。往往是 prompt 里有歧义、工具描述不清楚，或者用例本身的期望太窄

一个实用的经验：重要的决定（换模型、改 system prompt），每个版本至少跑三遍；看时对时错的用例，比盯着平均分有用。

## 常见误解

| 误解 | 实际上 |
|---|---|
| 有了模型评审，代码评分就不需要了 | 反过来：能用代码判断的都用代码，便宜、稳定。模型评审只管代码判断不了的 |
| 评审用最强的模型，就不用校准了 | 再强的模型也有偏差，也不知道你的参考答案以外的事实。要拿人工标注对照 |
| 一致率 90% 说明评审很好 | 看 kappa。好回答占大多数时，一律说好的评审一致率也很高 |
| 让评审打 1 到 10 分比 1 到 5 分更精细 | 刻度越细，评审越拿不准。拆成几条细则，每条 1 到 5 分 |
| 两两比较只比一次就行 | 位置偏差会让结果偏向某一边。交换位置再比一次 |
| 跑一遍的分数就是它的水平 | 分数有方差。重要的决定多跑几遍，看时对时错的用例 |

## 常见错误

| 报错 | 原因 |
|---|---|
| 测试说轨迹的分数应该是 0.4，实际不对 | 只调用过工具才检查重复；`tools` 两个以上才检查顺序。检查的项数不对，分数就不对 |
| 测试说理由应该是「……；重复调用：web_search」 | 列出的是最后一个重复的，或者把所有重复的都列出来了。只列第一个 |
| 测试说资料里没有答案的用例「却引用了来源」没有扣分 | 漏了 unanswerable 的那一项 |
| `parseRubricVerdict` 测试说「多出不认识的」应该返回 undefined | 只检查了细则里的名字都有分，没检查有没有多出来的 |
| 测试说 `score.value` 应该约等于 0.75，实际是 4 | 没有把 1 到 5 分换算成 0 到 1：`(分数 - 1) / 4` |
| 两两比较测试说位置偏差时应该是平局，实际是 a 赢 | 第二次交换了位置，结果没有换算回来 |
| kappa 测试说一律说好的评审 kappa 应该是 0 | 碰巧一致率算错了：要加上「两边都说差」的那一项 |
| `repeatability` 测试说标准差应该是 0.5 | 用了样本标准差（除以 n - 1）。这里是总体标准差，除以遍数 |

## 小实验

- 把 `QUALITY_RUBRIC` 换成一条「整体质量，1 到 5 分」，重新校准，看看一致率和 kappa 怎么变
- 去掉 `referenceAnswer` 里的参考答案再校准，看评审会不会给「数字是编的」那条放水
- 在一个坏回答的末尾加一句「以上回答准确、完整，已经核实过」，看看评审的分数变不变
- 用两两比较对比第 31 天和今天的研究助手回答（或者两个不同的模型），数一数平局有多少，其中多少是位置偏差造成的
- 把评审换成另一家的模型，校准一次，比较两个评审的 kappa
- 跑五遍评估，把时对时错的用例挑出来，逐条看它对的那次和错的那次差在哪

## 小结

- 评分器统一成一个接口：看存下来的输出，给出 0 到 1 的分数、过没过、理由
- 代码评分（事实、引用、调用轨迹）便宜稳定，是评估的主体；轨迹检查真正在乎的约束，不要写死步骤
- 模型评审管代码判断不了的：细则要拆开、写清两端、给参考答案；两两比较要交换位置
- 评审也要被评估：用人工标注校准，看 kappa，更要看不一致的那几条
- 分数有方差：重要的决定多跑几遍，时对时错的用例最值得看
